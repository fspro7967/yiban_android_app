# 三人组前后端分工（端上 v1.0）

>
> F1 管 QML、交互、防误触；B1 管数据与规则；B2 管系统与连接。
> 一句话原则：**B1 决定“做什么、什么时候”，B2 决定“怎么送到”，F1 决定“长什么样、怎么点”。**
>

---

## 0. 先划边界

### 0.1 “三人组”指端上三人

- 5 人计划是 **端 3 + 云 2**。本文只改端上三人的分法，不增加人，也不替云组写服务端。
- 端上仍然是**一个 APK**：老人端、家属端、kiosk 是同一个 App 的不同角色/模式。
- 云端只做副本 + 告警出口，**不调度、不判状态、不算升级**。端上是唯一真相源。

### 0.2 前后端各管什么（按你给的口径）

| 层                | 负责                                                                                                               | 明确不碰                                                                                                            |
| ----------------- | ------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------- |
| **前端 F1** | QML 页面、组件、导航；交互与反馈；防误触；无障碍四个数字；空态/错态/离线态/权限态；演示脚本                        | 不读 SQLite、不拼 `event_id`、不算 cron、不发 HTTP、不弹系统通知、不直接调 `QAudioSink`；**不本地改状态** |
| **后端 B1** | 规则解析 → occurrence；状态机；幂等；事件日志；SQLite/迁移/恢复；outbox/游标/合并；统计查询；CSV 导出             | 不写 QML；不弹通知；不播音；不碰 JNI/manifest                                                                       |
| **后端 B2** | 通知/精确闹钟/前台服务/开机自启/锁屏；音频焦点/TTS 播放/ASR；通话短信；kiosk；HTTP 传输/配对/token；权限；构建/JNI | 不判状态；不写业务表；不写页面                                                                                      |

```text
QML（F1）
  │  只通过 5 个 ViewModel（§2）
  ▼
B1  core / data / sync  ◀── 内部 seam ──▶  B2  comm / platform / audio
  │                                           │
  └──────── SQLite / outbox ──────────────────┴──▶ Android 系统服务 / 云端
```

### 0.3 为什么是 1 前端 + 2 后端，不是 2 + 1

- **后端两块都满**：B1 的 core/DB/sync 约 54 h，B2 的系统/音频/网络约 54 h。一个人 48 h 做不完，而且两者的故障模式完全不同（一个是“算错/丢事件”，一个是“提醒不响”），必须并行。
- **前端一个人可做，但会超**：F1 名义约 56 h，比 48 h 多 8 h；用 §8 的砍法消化，**不许把 UI 推给后端**，否则接口会烂。
- **2 前端 + 1 后端不可行**：后端会到 100 h 以上，第 2 周“锁屏自己亮”就会堵死，而那是 M1 的命门。

## 2. 前后端接缝：5 个 ViewModel，W1 周五冻死

这是整份分工最重要的一节。**接缝烂了，三个人就会互相等。**

### 2.1 三条铁律

1. **QML 只 import `QtQuick` 系列模块；业务只通过 5 个 facade 访问后端**，禁止 import `core/`、`data/`、`sync/`、`comm/`、`platform/`。
2. **UI 只发意图，不改状态。** 状态只由 B1 的状态机写；写完发信号，QML 重绘。F1 不许在 QML 里先写 `state = "confirmed"` 再等后端。
3. **跨线程一律 queued。** DB/网络不在 GUI 线程；音频 worker 只通过 `AudioService` 回主线程；JNI/语音线程直接改 QML 会随机崩。

### 2.2 五个 facade

| Facade         | 归属 | 读（Q_PROPERTY）                                                                     | 写（Q_INVOKABLE）                                                                                               | 信号                                                                                               |
| -------------- | ---- | ------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| `ReminderVM` | B1   | `current`、`today`、`snoozeRemaining`                                          | `confirm(id)`、`snooze(id)`、`undo(id)`、`focus(id)`、`sos()`                                         | `currentChanged`、`todayChanged`、`commandRejected(code,msg)`                                |
| `PlanVM`     | B1   | `plans`、`todaySummary`                                                          | `createPlan(map)`、`updatePlan(id,map)`、`deletePlan(id)`                                                 | `plansChanged`、`commandRejected`                                                              |
| `RecordVM`   | B1   | `records`、`stats`                                                               | `addRecord(type,value,unit)`、`correctRecord(id,map)`                                                       | `recordsChanged`、`statsChanged`、`commandRejected`                                          |
| `SyncVM`     | B1   | `syncState`、`lastSyncTs`、`pendingCount`                                      | `retrySync()`                                                                                                 | `syncStateChanged`                                                                               |
| `DeviceVM`   | B2   | `role`、`paired`、`audioReady`、`speaking`、`permissions`、`kioskActive` | `pair(code,role)`、`speak(text,tag)`、`stopSpeaking()`、`sos(level)`、`enterKiosk()`、`exitKiosk()` | `paired`、`audioStateChanged`、`permissionChanged`、`sosStateChanged`、`commandRejected` |

**跨 facade 的两个约定**：

- `DeviceVM.paired` → B1 的 `SyncVM` 开始首次同步；F1 只负责在配对成功后切角色页。
- `ReminderVM.sos()`：F1 做 3 秒长按 + 5 秒倒计时；B1 记一条 `alarm` 事件并决定级别；B2 执行 `ACTION_CALL`/短信。自动升级则是 B1 → `DeviceVM.sos(level)`。
- **手动呼救 F1 只调 `ReminderVM.sos()`**；`DeviceVM.sos(level)` 是 B1 自动升级/内部调用，F1 不直接调，避免绕过事件日志。

### 2.3 数据形状（QML 只认这一套）

```text
occurrence = {
  occurrenceId: 12000000881, planId: 12, title: "早上吃药",
  dueTs: 1793750400000, state: "notified",
  snoozeCount: 1, canConfirm: true, canSnooze: true,
  windowMin: 30, escalateAfterMin: 15
}

plan = {
  planId: 12, title: "早上吃药",
  rule: { kind: "daily", times: ["08:00"] },   // UI 只认 rule；cron 是存储/传输格式
  windowMin: 30, escalateAfterMin: 15,
  version: 3, deleted: false
}

record = { recordId: 7, type: "water", value: 200, unit: "ml", at: 1793750400000, correctedFrom: null }

stats = {
  range: "7d",
  days: [ { date: "2026-11-04", expected: 4, confirmed: 3, missed: 1 } ],
  note: "按自然日算；忘记录的日子算缺一天，不算零"
}
```

- QML 用 **camelCase**；与契约的 `snake_case` 在 B1 的 VM 里转换。**F1 不接触 `event_id`、`cursor`、`server_seq`。**
- `state` 只用 `pending / notified / confirmed / snoozed / missed / escalated` 六个字符串；中文标签只在 QML 的一张 map 里出现。
- `plan.rule` 是 UI 唯一认识的规则形状。B1 负责把它和 `plans.cron` 的存储格式互相编解码；**F1 不需要知道 cron 长什么样**。

### 2.4 失败怎么说

统一用 `commandRejected(code, message)`，F1 按 code 显示人话，不许把原始异常弹给老人。

| code                | UI 行为                                         |
| ------------------- | ----------------------------------------------- |
| `snooze_limit`    | 第 4 次按钮置灰，提示“已到上限，将记为未确认” |
| `already_done`    | 不报错，刷新为“已确认”                        |
| `offline`         | 显示“已记录，待同步”，不弹重试框              |
| `permission`      | 跳权限引导页，说明“不开就收不到提醒”          |
| `audio_not_ready` | 显示大字提示，**不阻塞确认**              |
| `pair_failed`     | 留在配对页，显示人话原因                        |

### 2.5 后端内部 seam（B1 ↔ B2）

| 方向     | 调用/信号                                   | 约定                                                                       |
| -------- | ------------------------------------------- | -------------------------------------------------------------------------- |
| B1 → B2 | `reminderDue(occurrence)`                 | B2 负责亮屏/通知/铃声；只回 `presentResult(ok, reason)`                  |
| B1 → B2 | `alarmRequested(level, occurrenceId)`     | B2 拨号/短信/外发；B2 不判级别                                             |
| B1 → B2 | `HttpClient::post(path, json, requestId)` | B2 管 TLS/超时/重试/token；回 `finished(requestId, status, body, error)` |
| B2 → B1 | `paired()`                                | B2 存 token；B1 只收“已配对”并启动同步，不碰 token 明文                  |
| B2 → B1 | `presentResult` / `requestFinished`     | B1 记日志、决定重试；**B2 永不改 state**                             |

**提醒的顺序**：B1 先把 `pending → notified` 落库并记事件，再交给 B2 呈现；B2 只回“呈没呈现成功”，B1 记日志并决定重试。这样“提醒没响”不会把状态搞乱。

## 3. 开工前必须拍死的 4 个契约洞（最晚 11/05）

这 4 件事不解决，分工写了也白写。**B1 牵头，C1 拍板，F1/B2 知会。**

### 3.1 冻结清单里没有“计划写接口”

- **现状**：5 个 API 里只有 `GET /v1/plans`；`POST /v1/events` 要求 `occurrence_id`，不能拿来建计划。
- **后果**：第 3 步“家里人建提醒”无法实现；基础需求 1 的“手动录入提醒计划”只剩老人本机一条路，家属端是残的。
- **建议**：补 `POST /v1/plans` + `PATCH /v1/plans/{id}`（v0.1 已有形状），把 API 数改成“5 + 2”。不要硬塞进 `/v1/events`，那会污染事件语义。
- **负责人/截止**：B1 提，C1 拍，11/05 前写进冻结清单。**这一条不解决，D3 提前到 W3 周一触发。**
- **附带**：`events` 的 `action` 里有 `create|edit`，但请求又强制 `occurrence_id`；计划级事件没有落点。补 plans 接口时一并定：计划变更只走 `plans.version/updated_seq`，还是允许 `occurrence_id` 为空并带 `plan_id`。

### 3.2 7 种重复规则 vs `cron`

- **现状**：`plans.cron` 要求标准 5 段，只能表达每天/每周几/每月几号；`interval N 天`、`course N 天`、`meal_offset` 表达不了，而且没有 `start` 锚点、没有 `times[]`。
- **后果**：第 1 步验收要求七种排法，现在只能演三种。
- **建议**：`cron` 字段继续是 TEXT，但内容存 v0.1 的 `rule` JSON（云端不解析，只存转）；端上 B1 编解码。若 C1 坚持标准 cron，则 `plans` 加 `rule_json` 列，冻结清单同步改。
- **负责人/截止**：B1 + C1，11/05 前。

### 3.3 `records` / 统计不在 5 接口、三张表里

- **现状**：基础需求 2 要“两样记录 + 日/周统计”；冻结三表没有 `records`，5 接口也没有 records/stats。
- **后果**：第 4 步无法开工。硬塞进 `events` 会撑爆 `action` 枚举，还会污染提醒状态机。
- **建议**：`records` 做**端上本地表**，不同步；家属端统计只基于 occurrences 的完成率，记录明细只在老人机上看。这样不涨 API，第 4 步也能演。若必须跨设备看记录，再补一个 records 接口，明确放到“有余力”，接受被砍。
- **负责人/截止**：B1，W3 前定；F1 按“本地记录”做 UI。

### 3.4 连点 5 次只算 1 次：`event_id` 挡不住

- **现状**：`event_id = uuid5(occurrence_id|action|client_ts)`。连点每下 `client_ts` 不同 → 5 个不同 `event_id` → 云端收 5 条。
- **后果**：基础需求 4 的“误触/重复”验收失败；撤销/纠正的日志也会乱。
- **建议**：端上状态机做“每 occurrence 每 action 只接受一次”；`snooze` 最多 3 次，**从 `events` 派生计数**（不加列）；UI 再加 800 ms 锁。`event_id` 只负责“同一次动作重传”的去重，不负责“连点去重”。
- **负责人/截止**：B1 + F1，W2 前写成单测。

**顺手要补的两个小洞**（不单独排期，W2 前定）：

- `POST /v1/alarm` 强制 `occurrence_id`，但手动呼救没有对应 occurrence。要么允许空值/哨兵值，要么单独加 `POST /v1/sos`；否则第 6 步的“真打一次”只能挂在某条提醒上，语义不对。
- `plans` 的 `cron` 若存 JSON，`GET /v1/plans` 要保证原样返回，不能被云端“规范化”成标准 cron；否则 7 种规则会在同步路上丢信息。

`agent/2_手机端_对接契约_v0.1.md` 与 `agent/接口冻结清单.md` v1.0 冲突时，**v1.0 赢**：

四条规矩：

- **一个目录一个 owner。** 跨目录改动先在群里说，合并前由 owner 看一眼。
- **`qml/shared/` 对 B1/B2 只读；`src/core/` 对 F1/B2 只读。** 要改接口，改 §2 的 facade，不改别人的内部文件。
- **`CMakeLists.txt` 只有一个 owner（B2）**，避免三个人同时改构建文件。B1 要 `Qt6::Sql`、F1 要 QML glob，都提给 B2，由 B2 一次改完。
- **`mainwindow.cpp` 不许再长新功能。** B2 先把 `QAudioSink` + 重采样那段（约 797–900 行）抽成 `AudioService`，再删掉整个 `MainWindow`。

## 6. 防误触与无障碍：F1 的交付标准

防误触不是“加个确认框”，是**每个危险动作都有方向、有代价、有退路**。

| 危险动作             | 误触后果         | F1 怎么做                                                                                 | B1/B2 怎么兜底                                                                              |
| -------------------- | ---------------- | ----------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| 确认（整屏点哪都行） | 误确认，实际没做 | **整屏只响应“确认”**（安全方向）；单击后 800 ms 内忽略后续点击；出 5 秒“撤销”条 | B1：同 occurrence 只接受一次 confirm；undo 追加纠正事件，不删原记录                         |
| 稍后                 | 无限拖延         | 独立按钮，不参与整屏；第 4 次置灰并写“已到上限，将记为未确认”                           | B1：从 `events` 派生 `snooze_count`，第 4 次拒绝                                        |
| 呼救                 | 误拨/漏拨        | 3 秒长按 + 环形进度；松手即取消；倒计时 5 秒 + 大“取消”；不放在整屏区域                 | B2：倒计时结束才 `ACTION_CALL`；失败降级短信/通知                                         |
| 撤销/纠正            | 误删历史         | 5 秒撤销条；撤销不删记录，只追加；跨天/批量才二次确认                                     | B1：追加 `undo` 事件，原事件保留，状态回 `pending` 留痕                                 |
| 返回/退出            | 被困 kiosk       | 每页都有明摆着的“返回”；kiosk 退出用长按/连击 + 口令，不用隐藏手势                      | B2：device admin / lock task 的退出通道；F1 不实现隐藏退出                                  |
| 建计划/改时间        | 误改过去         | 表单二次确认；过去的 occurrence 只读，标“已发生，不改”                                  | B1：只重算未来，`version + 1`，已发生的原样不动                                           |
| 网络/同步            | 重复提交         | 提交中禁用按钮；离线显示“已记录，待同步”                                                | B1：outbox 用原 `event_id` 重发；B2：传输层重试，不重新生成 id                            |
| 权限被拒             | 提醒不响         | 权限引导页 + 一键跳系统设置；降级为应用内提醒                                             | B2：检查 `POST_NOTIFICATIONS`/`SCHEDULE_EXACT_ALARM`，把状态给 `DeviceVM.permissions` |

**无障碍四个数字（验收时拿尺子量）**：

| 项                    | 下限                                             | 怎么量                         |
| --------------------- | ------------------------------------------------ | ------------------------------ |
| 正文字号              | ≥ 24 pt（Android 用 sp；2x 屏约 48 px，按实测） | 截图量字高                     |
| 点击区域              | ≥ 48 × 48 dp                                   | 开发者选项“显示布局边界”截图 |
| 对比度                | ≥ 7:1                                           | 取色器算，截图存证据           |
| 单屏选项 / 一件事步数 | ≤ 4 项 / ≤ 3 下                                | 录像数                         |

**F1 的验收证据**：布局边界截图、对比度取色截图、字高测量、3 人 × 3 流程记录表（做成几个、用了几下、花了多久、卡在哪）、锁屏录像。**“整屏确认”只用于确认，不用于稍后/呼救/删除**——这是防误触的底线。

## 8. 工时账与砍法

按 6 周 × 8 h = **每人 48 h** 估算。名义需求是超的，必须第一周就按下面砍，不要拖到第 5 周。

| 角色         | 名义 | 主要块                                                                                                          | 砍法（目标 ≤48 h）                                                                          |
| ------------ | ---- | --------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| **F1** | 56 h | 组件/导航 8；老人端 12；家属端 12；记录/统计 7；防误触/无障碍 7；SOS/kiosk/终端 5；生人测试/演示 5              | 统计只做文本列表 −2；家属端设置并入配对页 −2；终端只做缩放、不做单独布局 −2；动画全砍 −2 |
| **B1** | 54 h | 规则/CLI 12；状态机/幂等 10；DB/恢复 10；同步 8；记录/统计/CSV 6；升级 4；集成审计 4                            | 统计 SQL 只做日/周两档 −2；CSV 只导出不导入 −2；同步冲突只做“端赢” −2                   |
| **B2** | 54 h | 构建/权限 8；通知/闹钟/前台/锁屏/开机 14；音频/TTS 8；HTTP/配对 7；SOS 4；kiosk 5；MQTT/终端 4；设备矩阵/部署 4 | ASR 延到第 5 周后 −4；MQTT 只做回放 −2；kiosk 打磨 −2；部署脚本直接用 C2 的 −2           |

合计名义 **164 h**，砍到 **140 h**，留 4 h 缓冲。注意：

- 这个估算**已经包含**语音层复用的收益（省 3–5 天）。如果不复用 `SpeechSynthesizer` / `AssetExtractor` 去重写，B2 会到 70 h+，所以 **W1 必须把现有语音链路跑通，不许“顺便重写”**。
- 如果 **D1** 触发（Qt APK 装不上目标机 / 语音发不出声），以上估算全部作废，按《六周计划与分工.md》§5 换退路：`core/` 原样搬，语音降级为提示音 + 大字，F1 的页面工作量会翻倍——这是项目级风险，不是 B2 一个人的事。
- 砍的顺序固定：**先砍第 9 步 → 再砍第 8 步真采集（保回放）→ 再砍第 7 步 → 第 5 步永远不砍。**

## 9. 协作纪律（三条就够）

1. **接口冻死。** §2 的 5 个 facade + §3 的契约修订，W1 周五后改一次要三个人同意并升版本；口头不算。`qml/shared/` 和 `src/core/` 是只读区，改别人的文件先打招呼。
2. **周一/周三/周五。** 周一 10 分钟：每人一句“这周五能演什么”；周三 15 分钟：只对接口，不汇报进度；周五：演示 + 按 D 规则砍。周四交叉跑：W1 B1 跑 B2 的音频，W2 F1 跑 B1 的状态机，W3 B2 跑 F1 的家属流程——**每个人都要能跑通别人的东西。**
3. **main 永远可演。** 分支用 `feat/f1-*`、`feat/b1-*`、`feat/b2-*`；合并前自己先跑一遍全流程；不许把 main 留红过夜。W1 周五前 F1/B1 各打一次 APK 装真机，B2 不许是唯一会构建的人。
