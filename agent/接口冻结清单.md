## 0. 一句话架构

```
老人端(Qt/QML) ──┐
家属端(同 APK) ──┼→ 端上 SQLite（主副本）──→ 云（副本 + 告警出口）
Pi 终端(同一份 QML) ┘        调度、状态机、升级规则全在这里
```

- 端上是唯一真相源。**云不判定状态、不触发提醒、不计算升级。**
- 冲突规则：**端赢**。云端收到比 `since` 旧的数据，丢弃，不合并。
- 演示：云端起在 Pi 或笔记本上，手机连热点。不碰外网。

## 1. 状态枚举（写死，两端一个字都不许改）

```c
enum OccState {
    pending,     // 已排期，未到点
    notified,    // 已提醒，等确认
    confirmed,   // 老人确认"我做了"
    snoozed,     // 老人点了"等会儿"
    missed,      // 超时未确认
    escalated    // 已升级（通知家属）
};
```

状态迁移（只允许这 8 条）：

```
pending   --到点-->      notified
notified  --确认-->      confirmed
notified  --稍后-->      snoozed --到点-->      notified
notified  --超时-->      missed
missed    --升级-->      escalated
snoozed   --再次超时-->  missed
任何       --撤销/纠正--> pending      （走撤销接口，留痕）
```

`escalated` **不回退**。`confirmed` 之后不许再改状态，只能新开一条纠正记录。

## 2. HTTP API（5 个，不多不少）

统一约定：`Content-Type: application/json; charset=utf-8`，时间一律 `int` 毫秒 Unix 时间戳（不用字符串），鉴权头 `Authorization: Bearer <token>`。

### 2.1 `POST /v1/pair`

```json
请求 {"pair_code": "482913", "device_id": "android-a1b2c3", "role": "elder | family | terminal"}
响应 {"token": "eyJ...", "device_id": "android-a1b2c3", "cursor": 1024}
```

- `pair_code`：6 位数字，云端生成屏显 5 分钟有效，一次性。
- `device_id`：端上首次启动生成 UUID v4，存本地，卸载重装才算新设备。
- 失败：`404 pair_code_not_found` / `410 pair_code_expired`。

### 2.2 `POST /v1/events`（唯一高频写入口）

```json
请求 {"event_id": "uuid-string", "occurrence_id": 881, "action": "confirm",
      "ts": 1762345678901, "device_id": "android-a1b2c3", "reason": ""}
响应 201 {"accepted": true,  "server_seq": 1025}
响应 200 {"accepted": false, "server_seq": 1025, "dedup": true}   // 幂等命中
```

- `action` 只能取：`create | notify | confirm | snooze | miss | escalate | undo | edit`
- `reason`：仅 `undo/edit` 时非空，人话，如 `老人说记错了，改成 8 点`。
- **`event_id = uuid5(namespace, f"{occurrence_id}|{action}|{client_ts}")`**。
  `client_ts` 是动作发生时刻，不是提交时刻——断网攒 3 条重传时，三条的 `client_ts` 各不相同。
- **重复 `event_id` 必须被吞掉**：返回 200 + `dedup: true`，不写库、不增加 `server_seq`。
  这是"断网补传正好 3 条"的唯一实现方式。C1 要先写这条的测试，再写别的。
- `server_seq` 是云端单调递增整数，全库一个序列，**不复用**。

### 2.3 `GET /v1/plans?since=<cursor>`

```json
响应 {"plans": [{"plan_id": 12, "title": "早上吃药", "cron": "0 8 * * *",
                "window_min": 30, "escalate_after_min": 15,
                "version": 3, "updated_seq": 1030, "deleted": false}],
      "cursor": 1030}
```

- 家属端只在 `?since=` 增量拉；首次 `since=0`。
- `cron` 用标准 5 段，端上解析器必须自己实现或引入库，**不依赖云端算下一次到点时间**。
- `version`：同一 `plan_id` 每次改动 +1。端上按 `version` 覆盖，不按时间比。

### 2.4 `GET /v1/state?since=<cursor>`

```json
响应 {"states": [{"occurrence_id": 881, "state": "confirmed", "updated_seq": 1031}],
      "cursor": 1031}
```

- 只回状态与序号，不回明细。明细端上自己有。
- 家属端用它画"今天做了几件事"。

### 2.5 `POST /v1/alarm`（唯一出站口）

```json
请求 {"occurrence_id": 881, "level": 1, "reason": "未确认 15 分钟", "ts": 1762345678901}
响应 200 {"sent": true, "channel": "wecom"}
```

- `level`：`1` 提醒家属 / `2` 催办 / `3` 紧急呼救。
- 云端只负责外发（企业微信机器人 or ntfy），**不做重试判断**——重试由端上按自己的升级规则重发。
- `level: 3` 时云端必须**同时**打印一条到服务端 stdout（演示时看得见）。

### 错误码统一形状

```json
{"error": "dedup|auth|pair|bad_request|server", "detail": "人话"}
```

## 3. 三张表（字段即契约）

```sql
-- 端上与云端同名同字段，云端多两列：server_seq, device_id
plans(plan_id INTEGER PK, title TEXT, cron TEXT, window_min INT,
      escalate_after_min INT, version INT, updated_seq INT, deleted BOOL)

occurrences(occurrence_id INTEGER PK, plan_id INTEGER, due_ts INT,
            state TEXT, updated_seq INT, last_event_id TEXT)

events(event_id TEXT PK, occurrence_id INT, action TEXT, ts INT,
       device_id TEXT, reason TEXT, server_seq INT)
```

- `occurrences.occurrence_id` 由端上生成（`plan_id * 10^9 + 排期序号`），**不用自增**，否则离线两台机器会撞号。
- 云端 `occurrences` 只是镜像，**没有记录就是没同步过**，不许云端凭空生成 occurrence。

## 4. MQTT（Pi 终端与传感器，不上外网）

Broker：mosquitto 跑在 Pi，端口 1883，无 TLS（内网），`anonymous true` 开局，第 5 周有余力再加密码。

| topic | 方向 | payload |
| --- | --- | --- |
| `home/reminder/<device>` | 云/端 → 终端 | `{"occurrence_id":881,"title":"吃药","state":"notified","due_ts":...}` |
| `home/ack/<device>` | 终端 → 端 | `{"occurrence_id":881,"action":"confirm","ts":...}` |
| `home/alarm` | 端 → 终端 | `{"level":3,"occurrence_id":881}` |
| `home/sensor/presence` | ESP32 → 端 | `{"room":"bed","present":true,"ts":...}` |
| `home/terminal/ack` | 终端 → 云 | `{"msg_id":"uuid","ok":true}` |

- **QoS 1，`retain=false`**（保留消息会让重启后的终端演出鬼影）。
- 终端掉线不影响端上提醒——MQTT 只是"多一个显示器"，这是断网不变砖的延伸。

## 4.5 语音模块（复用既有 Qt/QML 语音助手）

语音也是契约，因为它横跨"谁写"和"锁屏能不能响"。

**优先级**：TTS（机器说话）是 P0——基础需求第 3 条要求"大字高对比 **语音返回**"；ASR（机器听懂）是 P1，第 2 周能不做就不做。

**分三层，别混在一起**（技术栈已实证，见 `复用清单.md`）：

```qml
// 层一·合成：已有（SpeechSynthesizer，sherpa-onnx + VITS，离线，出增量 PCM）
audio.speak(text, tag)   // tag 用于日志与打断判定
audio.stop()

// 层二·播放：新写 AudioService（QAudioSink + 8kHz→设备采样率重采样，
//   思路从 mainwindow.cpp:797-900 抽，别搬那个类）

// 层三·识别：已有 WhisperManager，但 P1，第 2 周不许碰
audio.listen(timeoutMs)  // 只回调，不阻塞
```

**规则**：

1. **TTS 天然离线**（ONNX 模型随 APK 走，输出 8 kHz），但**合成对了、喇叭没响 = 没做**。播放要能在锁屏/息屏下走通。
2. **ASR 失败必须在 3 秒内降级为按钮确认**，不许卡住提醒流程。认不出话是常态，不是异常。
3. **锁屏/息屏要能出声**：前台服务 + 音频焦点 `AUDIOFOCUS_GAIN_TRANSIENT_MAY_DUCK`；拿不到焦点时**不许硬播**，降级为通知音 + 大字。
4. **回调一律回主线程**再碰 QML 属性（`QMetaObject::invokeMethod(..., Qt::QueuedConnection)`）。JNI / 语音线程里直接改 QML 会崩，而且崩得随机。
5. **Pi 终端不复用手机 TTS。** 树莓派用 espeak-ng / piper，只复用 `speak/stop` 这两个接口签名，别把 Android 那一层搬过去。
6. 权限：`RECORD_AUDIO`、`FOREGROUND_SERVICE`、`POST_NOTIFICATIONS`，加 `SCHEDULE_EXACT_ALARM`（Android 13+ 必需）。

**验收一句话**：锁屏、息屏、断外网，按一下，手机把"该吃药了"念出来。

## 5. 事件日志 schema（答辩素材就靠它）

CSV 表头，一字不差：

```
ts,occurrence_id,event_id,actor,action,result,reason
1762345678901,881,uuid-a1,elder,confirm,ok,
1762345678901,882,uuid-a2,elder,snooze,ok,老人说等会儿
```

- `actor`：`elder | family | system | terminal`
- `result`：`ok | rejected | timeout | dup`
- 日志只追加，不修改。撤销也是追加一条 `undo`。

## 7. 文件归属（同一个 APK，三个人改，不划清必冲突）

```
app/
├── core/          ← 只有 A1 改（调度、状态机、日志、幂等）
├── ui_elder/      ← 只有 A2 改（提醒页、确认页、锁屏唤起）
├── ui_family/     ← 只有 A3 改（计划编辑、记录、统计）
├── net/           ← 只有 A1 改（HTTP 客户端、重传队列）
└── qml_shared/    ← 共同只读；要改先发群里说一声
```

- `core/` 改动必须带单测，且 `main` 上永远能跑。
- Pi 终端复用 `ui_elder/` + `qml_shared/`，**不许为终端另写一套页面**；屏幕尺寸差异用 `qml_shared/` 里的一个 `scale` 属性解决。
- 分支：`main` 永远可演；`feat/a2-锁屏提醒` 这种命名；合并前自己先跑一遍全流程。
