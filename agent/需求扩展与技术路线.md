# 独居老人生活助手 · 需求扩展与技术路线

> 输入：题目表格（work.xlsx，含基础要求 4 条 / 进阶要求 3 条 / 参考资料 4 项）、`需求分析.md`（产品形态与需求分层）、`前置知识学习路径.md`（团队现状与"暂不学"清单）。
>
> **本文档的假设**（写在最前面，错了请直接改，后面的结论会跟着变）：
>
> 1. 团队 4 人，大一，工程导论课程项目，可用时间约 **8 周 × 8 小时/人周**（课外）。
> 2. 团队里有 **1 人具备 Qt for Android 开发经验**（Qt/QML + 安卓打包上机），其余人无安卓/前端框架经验；已具备 git + AI 工具（见前置文档 P0–P4）。
> 3. 硬件预算合计 **≤ 800 元**；**已有一台已 root 的 Android 14 手机**可用于开发、演示与自动化测试。这两条是本次结论与前几版不同的关键前提（root 能解锁什么，见 §2.7 与附录 D）；不接受需要企业资质、备案、审核的东西（短信签名、医疗资质、上架）。
> 4. 交付判定 = **能现场演示 + 有可复查的记录/日志 + 覆盖表格要求**，不要求真实部署给老人长期使用。
> 5. "进阶"不是"锦上添花"，表格进阶要求 1（传感器）是**强制项**，所以每个形态都必须有一条接硬件的进阶路径。

## 0. 一页结论（先看这里）

| 决策                | 结论                                                                                               | 一句话理由                                                                                         |
| ------------------- | -------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| 主形态              | **Qt for Android**（形态 B4），老人端 + 家属端是同一个 APK 的两种模式                        | 队里已经有人会 Qt for Android，这条路最大的"环境杀手"不成立；而且同一份 QML 能直接编到树莓派当终端 |
| 同步与告警          | **MQTT（mosquitto）**，跑在树莓派上                                                          | 手机、终端、传感器都只连一个 broker，不需要写 HTTP 后端；演示开热点即零外部依赖                    |
| 专用设备 / 宠物终端 | **树莓派 + Qt eglfs**（E3-Qt），同一台机器兼作 broker                                        | 一台机器同时交"专用设备"和"宠物终端"两个作业点，Stage2 也落在它身上                                |
| 传感器              | **LD2410C 毫米波 + ESP32-S3 → MQTT**（F1）+ **F4 回放兜底**                           | 30–60 元，UART 直接出 JSON，不用写驱动；回放器保证演示不翻车                                      |
| 演示机 / 测试台     | **那台 root 过的 Android 14 手机**：`dumpsys` / `appops` / `svc` / `pm` 全程可脚本化 | 断网、重启、改系统时间、连点误触都能一条命令复现，见附录 D                                         |
| 明确不做            | 微信小程序、AOSP 编译刷机（已排除）、自研 ASR/TTS 模型、医疗诊断、真实 120 对接                    | 前两项团队已排除（见 §3.3）；后三项投入产出比与合规风险不划算；见 §2.9                           |
| 最大隐藏评分点      | **提醒不丢**（断电/重启/断网/时区）+ **误触可撤销** + **未确认升级链路**         | 表格基础要求第 4 条写得很轻，但这是唯一能证明"工程性"的地方                                        |

推荐组合一句话版：**B4（Qt 老人端）+ E3-Qt（树莓派终端，兼 broker）+ F1（雷达）+ root 安卓 14（演示与测试机）**——一份 QML 覆盖手机与终端，一条 MQTT 连接所有硬件，不加服务器。

几个必须知道的取舍（理由在后面各节）：

- **不再有小程序形态**。它拿不到精确闹钟、不能后台常驻，基础要求第 4 条的可靠性叙事直接断掉；而"老人不用装 App"这个优点，在你们有 root 设备、能把它变成"只跑我们一个 App 的专用机"之后，也不再是小程序独占。
- **不再走 AOSP**。编译刷机在学期内的时间和变砖风险都不划算；"专用设备感"用 root 设备（禁用系统桌面 + 锁定任务）一周内就能拿到 80%，见 §3.5 E2。
- **仍然要写一点 Java**。Qt 没有精确闹钟和通知的官方 API，必须 JNI 调 `AlarmManager` / `NotificationManager`，约 30–60 行。（有 root 之后这件事从"能不能"变成"必然行"，见 §3.2 B4。）

## 1. 题目拆解：字面要求背后的东西

### 1.1 逐词拆

| 题目里的词           | 它其实在要什么                 | 容易被忽略的工程点                                                         |
| -------------------- | ------------------------------ | -------------------------------------------------------------------------- |
| 独居                 | 没有人做兜底                   | 必须有**升级链路**（本人→家属→社区），否则"独居"这个前提不成立     |
| 日常提醒             | 重复计划 + 实例 + 状态         | 计划（plan）与实例（occurrence）必须分开，否则改计划会污染历史记录         |
| 信息记录             | 多类型、可补录、可纠错         | 记录要能**改**和**删**，且留痕；只能新增的记录等于不能纠错     |
| 支持大字体           | 可度量的无障碍规范             | 字号 pt、对比度比、点击目标 px、单屏选项数 —— 要给出数字，不能只说"很大" |
| 语音提示             | TTS 文案 + 触发时机 + 夜间策略 | 夜间要不要播？播多大声？重复几遍？这是交互设计，不是 API 调用              |
| 简单确认             | 单手势 + 防误触 + 免操作       | 最少步数 ≤ 3；误触要有 5 秒撤销；最优解是**不需要确认**（自动判定） |
| 用药计划提醒         | 药物安全边界                   | 漏服后**不能自动建议补服**；只提示"请联系医生/家属"                  |
| 作息记录             | 睡眠起止 + 基线                | 有基线才能谈"规律变化提示"（进阶要求 1 的落点）                            |
| 活动提醒             | 久坐、喝水、散步               | 与记录联动：记录了就不用提醒，避免重复打扰                                 |
| 传感器               | 事件源接入                     | 传感器只产出"事件"，业务判断在上层；适配层不能有业务逻辑                   |
| 室内跟随宠物外形终端 | 拟人化反馈语义                 | 灯光/表情/动作要有一张**语义表**（什么颜色=什么状态），否则是装饰品  |
| 实践需求分析         | 用户研究过程                   | 访谈提纲、观察记录、竞品截图、需求优先级依据                               |
| 事件管理             | 状态机 + 幂等                  | 提醒实例的状态迁移图；重复上报要去重                                       |
| 交互设计             | 原型 + 可用性测试              | 至少三种流程的测试记录（表格基础要求第 3 条直接写了）                      |
| 软硬件集成           | 通信协议 + 分层                | MQTT/HTTP 选一个，说清 topic 与 payload；硬件层不能直连数据库              |

### 1.2 表格基础要求 → 隐性验收点

| 要求                                               | 字面            | 隐性验收点（答辩会被问的）                                                         |
| -------------------------------------------------- | --------------- | ---------------------------------------------------------------------------------- |
| 1. 提醒计划 + 按时提示 + 确认 + 稍后 + 未确认记录  | 功能存在        | 稍后有没有次数上限？连续点 10 次稍后算什么？未确认记录能不能查、能不能被家属看到？ |
| 2. 睡眠起止、饮水、活动、饮食中两项 + 日/周统计    | 两项记录 + 图表 | 统计口径写清楚了吗（按天算还是按 24h 滚动）？漏记的那天算 0 还是算缺失？           |
| 3. 大字、高对比、语音播报、清晰返回 + 三种流程测试 | 界面 + 测试     | 三种流程具体是哪三种（用药/记录/呼救）？测试对象是谁、几个人、结论是什么？         |
| 4. 重复提醒、断网、重启、误触 + 事件日志           | 异常处理        | 断电重启后没执行的提醒会补吗？断网期间的操作联网后会不会重复写？日志能不能导出？   |

**结论**：基础要求里真正拉开差距的是第 4 条。建议把"可靠性"当成一个正式模块做（`core/` 里的状态机 + append-only 日志 + 幂等键），而不是散落在各处的 `if`。

## 2. 需求扩展：还能提出哪些可能需求

### 2.0 需求从哪里长出来（五种来源，避免拍脑袋）

1. **角色**：老人本人 / 同城子女 / 异地子女 / 社区网格员 / 上门护工 / 医生。每个角色关心的东西不同，家属要"知道"，老人要"不用管"。
2. **时间线**：睡前 → 起床 → 早餐（服药）→ 外出 → 午餐 → 午睡 → 活动 → 晚餐（服药）→ 洗漱 → 夜间起夜。把一天铺开，缺口自己会浮出来。
3. **异常**：没确认、重复点、记错、断网、断电、换手机、外出未归、夜间长静、设备离线。
4. **无障碍**：视力（字号/对比度/读屏）、听力（音量/震动/灯光）、行动（步数/目标尺寸）、认知（选项数/文案/防误操作）、语言（方言/语速）。
5. **工程性**：幂等、可回放、可测试、可导出、可解释（为什么今天提醒了三次）。

### 2.7 系统级能力（那台 root 的 Android 14 解锁的一整类需求）

普通 App 在安卓上做"提醒助手"，天花板不是代码，是系统策略：精确闹钟被默认拒绝、后台服务会被杀、状态栏会露出别的 App、系统桌面一按就回主屏。**你们那台 root 过的 Android 14 手机，把这层天花板拆掉了**——这既是一批新需求，也是"减少老人操作"最硬的落地方式。

| 编号  | 可能需求                                                    | 最小实现                                                                                                                                                                                      | 判定"做了"的证据                                                                                 | 优先级 |
| ----- | ----------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ | ------ |
| R8-1  | 精确闹钟强制授权                                            | Android 14 起 `SCHEDULE_EXACT_ALARM` 对新装应用默认拒绝；root 下 `adb shell appops set <pkg> SCHEDULE_EXACT_ALARM allow`（免去引导用户进设置的 3 层菜单）                                 | `dumpsys alarm \| grep <pkg>` 能看到 `setExactAndAllowWhileIdle` 的条目 + 到点误差 P95 ≤ 5 s | P0     |
| R8-2  | 电量优化白名单（Doze 不漂移）                               | `adb shell cmd deviceidle whitelist +<pkg>`；否则 Doze 下闹钟可能延后数分钟                                                                                                                 | 息屏待机 8 h 后仍准时（录屏 + 日志时间戳）                                                       | P0     |
| R8-3  | 前台服务常驻（Android 14 必须声明类型）                     | `AndroidManifest` 里 `android:foregroundServiceType="specialUse"`（或 `dataSync`），否则启动即崩 `MissingForegroundServiceTypeException`；`startForeground(id, notification, type)` | 常驻通知不消失；`adb shell am force-stop` 后 30 s 内自恢复                                     | P0     |
| R8-4  | 开机自恢复（不靠启服务）                                    | `RECEIVE_BOOT_COMPLETED` 的 receiver 里**只重排未来 24 h 的闹钟，不启动前台服务**（Android 12+ 对 boot 后启动 FGS 有限制）                                                            | `adb reboot` 后 60 s 内界面自启、未完成实例恢复                                                | P0     |

**纪律（root 是有代价的，写进报告反而加分）**

- 演示前用 TWRP/Magisk 做一次全盘备份，出问题 5 分钟恢复；**这台机器只当演示与测试机，不要装日常账号**。
- 只装来源明确的 Magisk 模块（Zygisk/LSPosed 之类）；系统 OTA 升级会掉 root，答辩前**不要点系统更新**。
- root 只是让"系统策略"可配置，**不要用它去绕过用户的确认**——那会把产品变成监控工具，答辩一问就崩。

**为什么这批需求值得写进文档**：题目说"尽量减少老人的操作"。在系统层，"少操作"就是 R8-1（不用教老人去开权限）、R8-5（不用教老人认桌面）、R8-6（不用教老人忽略状态栏）。**它们比任何一条 UI 细节都更能支撑这句话。**

### 3.1 形态 A：Web / PWA（家属端形态 + 兜底方案）

**定位变了**：主形态定成 B4（Qt）之后，A 不再是"主产品"，而是两个角色——① **家属端的另一种实现**（家属多在电脑/手机上用，浏览器最省事，见 A2）；② **兜底方案**（万一 Qt 的工具链翻车，整队能在一周内退回到这里，业务代码的领域模型不变）。

老人端在浏览器打开，家属端在同一后端的另一个页面。**这是唯一一条"三端（手机/电脑/大屏终端）零重复开发"的路线**，也是 E3（Chromium kiosk）的基础。

#### A1 · 纯前端本地优先（无后端，兜底用）

**技术栈**：Vite + 原生 TS/JS（或 Vue 3，仅当有人愿意学）、IndexedDB（Dexie）、Service Worker（Workbox）、Web Speech API（`speechSynthesis`）、Notification API + 页面内全屏提醒层、Chart.js 或手写 SVG。

**基础阶段（约 2 周）**

- 范围：提醒 CRUD、7 种重复规则、到点检测（`setInterval` 30 s + `visibilitychange` 回来时校正）、确认/稍后（3 次上限）、两类记录、日/周统计、三档字号主题、事件日志（只追加）。
- 关键实现：调度用"每 30 s 扫一遍到期实例"而不是"为每条提醒设一个 timer"——后者在页面切后台、锁屏、休眠后必然丢。扫表法 + `localStorage` 存 `lastScanAt`，回来一次补齐。
- 交付物：可安装的 PWA、演示脚本、3 条流程测试记录、`docs/数据模型.md`。
- 验收：断网后仍可提醒与记录；刷新页面不重复弹同一条。

**进阶阶段（约 2 周）**

- 加后端推送（Web Push + VAPID，需要一个小服务）；或用 **ntfy/Gotify 自建推送**（Android 可用，iOS 需 PWA 安装 + 16.4+）。
- 用 Capacitor 把同一套代码打成 APK（`npx cap add android`），获得系统级通知与后台能力——这是"Web 路线转 App"的最短路径。
- 接终端：WebSocket 或 MQTT over WS，把提醒状态同步给宠物终端（灯光/表情）。
- 接传感器：走 MQTT Broker，前端只订阅。

**坑与规避**

- 页面关闭 = 没有提醒。必须承认并给出方案：要么常开（E3 kiosk 正好），要么上推送，要么退化到"打开时补提醒 + 补记录"。
- `SpeechRecognition` 在 Chrome 依赖 Google 在线服务，国内基本不可用 → ASR 放后端（Whisper.cpp / 阿里云一句话识别），前端只做 TTS。
- `speechSynthesis` 各平台音色差异大，Android Chrome 中文音色可能很机械 → 关键提醒用**预录音频**兜底。
- 通知需要 HTTPS（localhost 除外）→ 用 `mkcert` 本地证书或内网自签。

**评分覆盖**：基础 1/2/3/4 全 · 进阶 1（需外接）· 进阶 2（需外接）· 进阶 3（语音交流可做，营养查询可做）
**适合**：想最快出可用东西、且不排斥"终端 + 浏览器"组合的队伍；在本方案里是**兜底**。

#### A2 · 前端 + 轻后端（家属端 Web 版 / 兜底主力）

**技术栈**：前端同 A1（或 React/Vue）；后端 **FastAPI（Python）** 或 Node + Express；**SQLite** + SQLModel/Prisma；调度用 APScheduler / node-cron（**服务端调度，不依赖页面存活**）；WebSocket 推送；Nginx 反代；Docker Compose 一键起。

**基础阶段（约 2–3 周）**

- 范围：提醒存后端、服务端定时扫描到期 → 通过 WebSocket 推给在线老人端 + 落库"待确认"；老人端确认/稍后回写；家属端建计划、看日志；两类记录与统计；三档主题。
- 关键实现：
  - 实例表带 `state`（pending / notified / confirmed / snoozed / missed / escalated）与 `notified_at`、`confirmed_at`，**状态迁移只允许走一个函数**（`core/state_machine.py`），所有入口（UI、语音、家属端）都调它。
  - 幂等：写日志用 `event_id = uuid5(occurrence_id, action, client_ts)`，重复提交直接吞掉 —— 断网补传天然安全。
  - 日志 append-only（只插不改），另建"更正"事件来纠错，保证可回放。
- 交付物：`docker compose up` 即跑、API 文档（FastAPI 自带 `/docs`）、日志导出 CSV。
- 验收：关掉老人端页面，提醒仍然在服务端按时触发并留下 `notified` 记录；重连后补推。

**进阶阶段（约 2–3 周）**

- 部署：1 核 2G 学生机（约 50–100 元/月）或内网 + frp；HTTPS（Caddy 自动证书最省事）。
- MQTT（Mosquitto/EMQX）作为设备总线：`home/reminder/+/state`、`home/sensor/presence`、`home/terminal/ack`。后端同时是 MQTT 客户端与 WebSocket 服务端 → 硬件与前端解耦。
- Web Push / 家属微信通知（企业微信机器人 webhook 最省事，免费、无需审核）。
- 权限：老人/家属/社区三角色，JWT + 服务端校验。
- 数据层：从 SQLite 迁 PostgreSQL 只改连接串（用 SQLModel/SQLAlchemy 时注意别用 SQLite 特有语法）。

**坑与规避**

- 后端一挂全挂 → 老人端必须能**离线继续提醒与记录**，联网补传（前端 IndexedDB 缓存 + 队列）。
- 公网暴露 = 被扫。至少：强密码、限流、关掉 `/docs`（或加鉴权）、别用默认端口。
- 时区：服务端统一 UTC 存储，展示按老人所在时区；别用 naive datetime。
- SQLite 并发写会锁 → 单进程 + WAL 模式够用，别开多 worker。

**评分覆盖**：基础 4 条全（最扎实）· 进阶 1/2（MQTT 接）· 进阶 3（后端做 ASR/LLM 代理最自然）
**适合**：家属端要多端访问、或需要"服务端调度"这个卖点时。**注意**：本方案的主形态已改为 B4，A2 的角色是"家属端 Web 版 + Qt 翻车后的兜底"；如果只做家属端，A2 可以砍到"两个页面 + 一个 FastAPI"，一周内能出。

#### A3 · 借 Home Assistant 当引擎

**技术栈**：Home Assistant Core（Docker）+ MQTT + ESPHome + 自定义 Lovelace 卡片（Lit/TS）；提醒用 `automation` + `timer` + `notify`，历史用 `recorder`，统计用 `statistics` 传感器。

**基础阶段（约 1–2 周）**

- 范围：用 HA 的自动化覆盖提醒与升级链，用 HA 面板（kiosk 浏览器全屏）当老人界面；记录用 `input_*` 辅助实体或 `influxdb`。
- 关键实现：HA 的 `timer` 实体天然带 `active/paused/idle` 与 `finished` 事件 → 稍后提醒就是 `timer.start` 再来一次，省掉自己写状态机。

**进阶阶段（约 2 周）**

- 写自定义卡片（`custom:button-card` 或自研 Lit 组件）做大字界面；接 ESPHome（ESP32 传感器/终端）几乎零代码；接 LLM 集成做对话。
- 用 HA 的 `history` + `statistics` 出趋势图；用 ` recorder` 的 SQLite 直接查。

**坑与规避**

- **最大的坑是评分**：答辩时"这是你自己写的吗"很难答。定位要明确——**HA 只作设备接入/自动化联调环境与参考架构**，主产品仍是自己写的 B4（Qt）。
- HA 学习曲线陡（YAML、实体、模板），对大一不友好；版本升级常破配置。
- HA 前端不适合做精细的老人交互（大字/单手势），别硬改。

**评分覆盖**：基础 2/4（借来）· 进阶 1/2（强）
**适合**：队里有人愿意啃 HA，且只把它当"硬件联调台"。

#### B4 · Qt for Android（Qt Quick/QML + C++）——**本方案首选**

**先给结论**：Qt 是唯一能做到"**一份 QML 同时跑安卓手机、树莓派全屏终端、桌面调试图**"的方案。它曾经是高风险选项，但你们组的两条现实把它变成了默认答案：

1. **队里有人真的做过 Qt for Android**。这条路最大的杀手从来不是 C++ 或 QML，而是 JDK/NDK/SDK/Gradle 的版本矩阵——有人踩过一遍，这一步从"一到两周的悬崖"降到"两三天"。
2. **有一台 root 过的 Android 14 手机**。Qt 在安卓上最难受的三件事（精确闹钟被拒、后台被系统杀、退不出自家界面）全部变成"一条命令能配好"，而且每一步都能用 `adb`/`dumpsys` 验证。详见 §2.7 与下面的对照表。
3. **不需要写 HTTP 后端**。手机、树莓派、ESP32 都连树莓派上的 mosquitto，Qt 侧用 Paho C++ 客户端；同步、告警、终端联动走同一套 topic。少一个服务就少一类故障。

**还需要过的"半关"**（前两关已经过了，这一关是新增的）：

| 只剩的关卡                              | 现状                                                              | 怎么办                                                                                                                                                                                            |
| --------------------------------------- | ----------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| JNI 边界：闹钟/通知/前台服务必须写 Java | 绕不开，Android 没有官方 Qt API                                   | 把范围压到 3 个类：`AlarmReceiver`（约 20 行）、`NotifyHelper`（约 30 行）、`FgService`（约 40 行）。**把它们当成"平台适配层"，而不是"被迫的黑科技"**——报告里画清这条边界就是加分项 |
| Qt 生态小，AI 辅助效果差                | QML 训练语料远少于 React/Flutter，dsh/Kilo 生成 QML 常有 API 幻觉 | 只让 AI 写"数据绑定 + 布局"，C++ 逻辑自己写；遇到 QML 报错先查 `qmlscene`/`qmlformat`，别信 AI 的记忆                                                                                         |
| 跨架构：同一份代码要编到 aarch64        | E3-Qt 才需要，第一阶段不碰                                        | 先在 Pi 本机编译（不交叉编译），跑通再谈 sysroot                                                                                                                                                  |

**技术栈**：Qt 6.8 LTS（开源版）+ Qt Quick / QML + Qt Quick Controls；C++17 写业务；QtSql + SQLite；QTextToSpeech（TTS）；Qt Network（WebSocket/HTTP）；**Eclipse Paho C++**（MQTT，别用 QtMqtt，许可证见附录 C）；Qt Creator 的 Android kit + **JDK 17** + **NDK r26/r27** + Android SDK Platform 34/35 + Gradle（版本组合照 Qt 官方文档的对照表配，别自己拼）；`androiddeployqt` 出 APK。

- 目标机是 **Android 14（API 34）**：`minSdk 28`、`targetSdk 34` 起步；把 `targetSdk` 定在 34 意味着下面所有 Android 14 的强制项都会生效，**这是好事**——踩过的坑都能写进报告。
- JNI 用 Qt 6 的 **`QJniObject` / `QJniEnvironment`**（`QAndroidJniObject` 是 Qt 5 的旧名，别抄到旧教程）。

**基础阶段（约 3 周，含 4 天环境）**

- 范围：提醒 CRUD、7 种重复规则、到点提醒（精确闹钟）、确认/稍后/未确认、两类记录、日/周统计、三档大字主题、事件日志落 SQLite、开机自恢复。
- **D1–D3 环境**：Qt 在线安装器装 6.8 + Android 组件；Qt Creator → Preferences → Devices → Android 里 SDK/NDK/JDK 三个路径全绿；Hello World 装进那台 root 安卓 14。有人带过，这一步的止损线放宽到 **4 天**（过不了再谈退路，见 §4.2）。
- **D4–D10 领域层**：`core/` 用纯 C++ 写（不依赖 QML、不依赖 Android），`plan` / `occurrence` / `log` 三张表 + 状态机；用 `QTest` 跑 7 种规则与"假时钟"单测（把时间来源抽成 `Clock` 接口注入，测试里一天 = 一秒）。
- **D11–D18 界面与提醒**：
  - QML 只做绑定与动画，业务全在 `QObject` 里，用 `qmlRegisterType` / `setContextProperty` 暴露。**QML 里出现业务 `if`，后面就没法测。**
  - 大字体：`QFontDatabase::addApplicationFont` 嵌 Noto Sans SC + 全局 `uiScale`，别逐处硬编码字号——这是 Qt 相对 Web 的真实优势，字体一定一致，不受系统字体影响。
  - 统计图：**别用 Qt Charts**（GPL/商业，见附录 C），用 `Canvas` 或 `QtQuick.Shapes` 画柱状图，20 行 QML 够。
- **提醒链（本方案的技术核心，约 50 行 Java + 80 行 C++）**：
  1. C++ 算出下一次 `due_at`，`QJniObject` 调 Java 静态方法 `scheduleAlarm(long triggerAtMillis, int occurrenceId)`；
  2. Java 侧 `AlarmManager.setExactAndAllowWhileIdle(RTC_WAKEUP, …)` + `PendingIntent`（**必须 `FLAG_IMMUTABLE`**）指向 `AlarmReceiver`；
  3. `AlarmReceiver.onReceive` → `NotificationManager.notify(channelId, …)`（Android 8+ 必须先建 channel）→ 回调 C++；
  4. 确认/稍后 → C++ 更新 state → 取消/重排闹钟 → 写日志（**唯一能改状态的地方**）；
  5. 开机 → `BOOT_COMPLETED` receiver **只重排未来 24 h 的闹钟，不启前台服务**（原因见下面的 Android 14 坑表）。
- **root 设备的三行准备**（写成 `scripts/setup_device.sh`，演示前跑一遍）：
  ```bash
  adb shell appops set com.you.elder SCHEDULE_EXACT_ALARM allow          # R8-1 精确闹钟
  adb shell cmd deviceidle whitelist +com.you.elder                      # R8-2 免 Doze 漂移
  adb shell pm grant com.you.elder android.permission.POST_NOTIFICATIONS  # 免手点授权
  ```
- 交付物：APK + 真机录屏 + 《Qt Android 环境搭建踩坑记录》+ `setup_device.sh`（三样都是加分材料，尤其最后一样——它证明你们会自动化）。

**进阶阶段（约 3 周）**

- **同一份 QML 跑树莓派**：`./elderly-helper -platform eglfs` 全屏无桌面 + systemd 拉起 → **E3-Qt**，开机到界面 5 s 内。手机、终端、桌面三处零重复开发，而且没有浏览器那一层。这台 Pi 同时跑 mosquitto，于是**"专用设备 + 宠物终端 + 消息总线"三合一，只花一份硬件的钱**。
- **家属端**：同一个 APK 的"家庭模式"（启动时输配对码进另一套 QML 视图），建计划 / 看日报 / 收告警。省掉第二套 UI，也省掉"家属要装第二个 App"。家属想用电脑时，再补 A2 的一个 Web 页面（可选）。
- 通知与锁屏：JNI 调 `NotificationManager`；锁屏唤醒要 `setShowWhenLocked` / `setTurnScreenOn`，同样是 JNI。
- 语音：`QTextToSpeech`（走系统 TTS 引擎，中文可用但机械）；**ASR 没有官方模块** → 二选一：(a) JNI 调 `SpeechRecognizer`（本地/在线取决于系统，Android 14 上要 `RECORD_AUDIO` + 联网）；(b) 手机录音上传到 Pi，Pi 上跑 `whisper.cpp` 小模型（**中文效果好得多，且离线**，推荐）。
- 硬件：MQTT 用 **Paho C++**；安卓上串口要 USB Host + `usb-serial-for-android`，Qt SerialPort 不支持安卓 USB 串口 → **让 ESP32 走 Wi-Fi/MQTT，手机根本不碰串口**（`/dev/ttyUSB*` 直连只在 §2.7 R8-11 里当实验）。
- 宠物表情：`PropertyAnimation` + `Canvas` 画眼睛；同一份 QML 在 Pi 上就是"桌面宠物"，在手机上就是"会眨眼的提醒卡片"——这是能实拍的差异化。
- **root 手机当 kiosk**（§3.5 E2）：装自有 Launcher + `set-home-activity` + `policy_control immersive.full=*`，一台日常手机 10 分钟变成"只能跑我们 App 的老人机"。**这条几乎零成本，但演示时冲击力最强。**
- 顺带：`Qt for WebAssembly` 能把同一套 QML 编成网页版（包体 15–25 MB、无 TTS、单线程），**只用于答辩时在评委电脑上免安装演示**，不要当产品形态。

**Android 14（API 34）专属坑表——这些在通用教程里查不到**

| 现象                                                 | 原因                                                                                   | 处理                                                                                                                                                                                                        |
| ---------------------------------------------------- | -------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 一启动就崩 `MissingForegroundServiceTypeException` | Android 14 强制前台服务声明类型                                                        | manifest 加 `android:foregroundServiceType="specialUse"` + `<property android:name="android.app.PROPERTY_SPECIAL_USE_FGS_SUBTYPE" android:value="elderly_reminder"/>`；`startForeground(id, n, type)` |
| 闹钟不响 / 误差几分钟                                | Android 14 起 `SCHEDULE_EXACT_ALARM` 对新装应用**默认拒绝**（targetSdk ≥ 33） | 先 `canScheduleExactAlarms()` 检查再引导；root 机一条 `appops`（R8-1）。**别指望 `USE_EXACT_ALARM`**：它只给闹钟/日历类应用，商店审核会拒                                                       |
| Doze 下提醒迟到                                      | 电池优化                                                                               | `cmd deviceidle whitelist +<pkg>`（R8-2）                                                                                                                                                                 |
| 重启后什么都不工作                                   | 开机广播里启动前台服务被限制                                                           | **只重排闹钟、不启服务**（R8-4）；界面等用户打开时恢复                                                                                                                                                |
| 动态注册的 receiver 收不到                           | Android 14 要求显式 `RECEIVER_EXPORTED` / `RECEIVER_NOT_EXPORTED`                  | `registerReceiver(r, filter, RECEIVER_NOT_EXPORTED)`                                                                                                                                                      |
| `PendingIntent` 报错                               | Android 12+ 必须显式可变性                                                             | `FLAG_IMMUTABLE`（要覆盖旧值时再或 `FLAG_UPDATE_CURRENT`）                                                                                                                                              |
| 通知不显示                                           | `POST_NOTIFICATIONS` 是运行时权限                                                    | `adb shell pm grant …`（调试机）/ 首启引导                                                                                                                                                               |
| 装了但不自启                                         | 厂商省电策略                                                                           | root 白名单 + 前台服务；**别在报告里承诺"所有手机都自启"**                                                                                                                                            |

**root 之后，这些痛点直接消失（这张表就是答辩时的"为什么用 root"）**

| 普通 App 的痛点                             | root 后                                                         |
| ------------------------------------------- | --------------------------------------------------------------- |
| 精确闹钟要教老人点 3 层设置                 | 一条 `appops` 命令（R8-1）                                    |
| 后台被省电策略杀                            | `deviceidle whitelist`，必要时装成系统应用（R8-2）            |
| 退不出自家界面（要恢复出厂设 Device Owner） | 禁用系统 Launcher + `set-home-activity`（R8-5，见 E2）        |
| 状态栏露出别的 App 的通知                   | `policy_control immersive.full=*`（R8-6）                     |
| 没法自动化测"断网/改时间/连点"              | `svc` / `settings` / `input` 全可脚本化（R8-9，见附录 D） |

**坑与规避**

- **止损线**：4 天内没在真机上跑起来 → 启动 §4.2 的退路，并把已写的 `core/` 业务逻辑直接搬过去（领域模型与语言无关，这是分层的回报）。
- 冷启动 1–3 s（加载 Qt 库），表格没要求，但别在"减少老人操作"的叙事里吹"秒开"。
- **无障碍**：Qt 不把 QML 暴露给 TalkBack，读屏基本不可用。表格基础要求 3 只要求大字/高对比/语音，不致命；但**别在报告里写"支持读屏"**——不如老实写"这部分换原生 Android 会更好"，反而显得懂行。
- **AI 辅助效果差**：QML 训练语料远少于 React/Flutter，dsh/Kilo 生成的 QML 常有 API 幻觉。你们的工作流是 AI 辅助，这条要算进成本——这是它相对 A2/B1 最被低估的劣势。
- 包体 20–40 MB；`androiddeployqt --release` + keystore 签名别忘，debug 包在别人手机上装不上、还卡。
- 别静态链接 Qt（LGPL 要求可重链接）。
- **演示纪律**：演示前跑一遍 `scripts/chaos.sh` + 做一次 TWRP 备份；root 机不登日常账号、答辩前不点系统更新。

**评分覆盖**：基础 4 条全（含系统级保障 R8-1/4/9）· 进阶 1（MQTT）· 进阶 2（**强**，Pi 复用同一 QML 当桌面宠物）· 进阶 3（ASR 走 `SpeechRecognizer` 或 Pi 上的 whisper.cpp）
**适合**：**你们组就是这一类**——有人会 Qt for Android、手上有 root 设备、且想要"手机 + 终端一套代码 + 可脚本化验证"的三重收益。**代价诚实地说**：约 50–80 行 Java 胶水、AI 辅助对 QML 效果差、无障碍不如原生。这三条都写进报告，比藏起来强。

### 3.3 已排除的两个形态（决策记录，不进候选）

工程文档里"不做什么 + 为什么"和"做什么"一样重要——答辩时被问"为什么不考虑小程序 / 不做定制 ROM"，这一节就是答案。**注意：这里不是候选方案，不要在这里花时间。**

#### 3.3.1 微信小程序（已排除）

**它曾经的优势**（不承认这点，显得没认真比较过）：

- 中国老人大概率已经装好微信，**不用安装**是最大的"减少操作"；
- 家属转发一张卡片就能加入，拉新成本最低；
- 前端门槛低，两周能出可用版本。

**排除它的硬理由**

1. **提醒可靠性有天花板**。小程序不能后台常驻、不能注册精确闹钟，到点提醒只能靠**订阅消息**；而订阅消息是"用户每授权一次，才允许发一条"。老人确认一次才攒一条额度，额度耗尽就得再引导他授权。表格基础要求第 4 条（重复提醒、断网、重启后的可靠性）在这条路线上**没有干净解法**：云端定时触发器只能把消息发出去，唤不醒一个小程序。
2. **拿不到系统能力**。锁屏全屏、开机自启、免打扰控制、替换桌面，全都没有。你们那台 root 安卓 14 能做的事，小程序一件都做不到。
3. **和最终形态不匹配**。既然 Stage2 要做"老人的专用机"（E2 / E3-Qt），终端上跑的是我们自己的程序，小程序最多只能做家属端——而家属端用同一个 App 的"家庭模式"就解决了（§3.2 B4 进阶阶段）。

**结论**：从小程序候选里删除。将来若真需要"零安装"的家属入口，用**企业微信机器人 webhook** 发通知即可（免费、不用审核、不用备案），成本远低于做一个小程序。

#### 3.3.2 AOSP / LineageOS 定制刷机（已排除）

**它曾经的目标**：把需求分析里"定制手机 ROM"落成真的系统镜像——预装我们的 App、换掉桌面、改默认权限、开机即用。

**排除它的硬理由**

1. **时间成本不可控**：源码同步 + 首次编译就是半天到一天起步，出错信息晦涩（vendor blob、内核版本、设备树不匹配），一个驱动问题能吞掉一周。
2. **变砖风险落在演示日**：学期内很难保证"随时能稳定刷回去"，而演示当天手机变砖是不可接受的失败模式。
3. **收益已经被 root 设备吃掉 80%**：`pm disable-user` 掉系统桌面、`cmd package set-home-activity`、`settings put global policy_control immersive.full=*`、`appops` 授权——在 root 设备上**一条命令**就完成，不需要编译任何镜像（见 §3.5 E2）。真 ROM 唯一多出来的是"改开机动画 / 预置到系统分区"，对评分没有增量。

**结论**：AOSP 从候选里删除，但**保留在报告的"方案比较"章节**：写清"我们评估过定制 ROM，基于上述三条选择 root 设备 + kiosk"，这段本身就是很好的工程决策论证（比"我们没想过"强得多）。

**如果还想要一点"ROM 感"**（可选，半天）：用 Magisk 模块换开机动画、把 APK 装进 `/system/priv-app` 拿系统签名权限——十分钟的事，答辩时够讲了。

### 3.4 形态 D：专用终端（宠物外形）

题目进阶要求 2 点名"固定桌面宠物终端"或"移动宠物终端"，且要"灯光、表情或简单动作反馈"。这一节是**加分主战场**，也是"软硬件集成"唯一能实拍的部分。

#### D1 · 树莓派 / 香橙派 + Python

> **在主方案里，D1 与 E3-Qt 是同一台机器**：装的是 Qt eglfs 版（§3.5 E3-Qt），不是这一节的 Python 版。保留下面的 Python 路线，是给"终端与主程序彻底分离、各写各的"的备选场景——那种情况下终端 Python、手机 Qt，中间靠 MQTT 解耦，也能跑，但多一套语言和一套状态同步。

**技术栈**：Pi 4B(2G) / Pi Zero 2W / 香橙派 Zero3；Python 3.11；`gpiozero`；`paho-mqtt`；本地 FastAPI（可选）；WS2812 灯环（`rpi_ws281x`）；SG90 舵机（耳朵/尾巴）；**Piper TTS**（离线中文 `zh_CN-huayan`）；`openWakeWord`；MediaPipe（摄像头）。

**基础阶段（约 2–3 周）**

- 范围：终端只做三件事——**显示 + 声光 + 一个大按钮**。MQTT 订阅 `home/reminder/#` → 灯环呼吸（待办）/常亮（待确认）+ 语音播报 + 大按钮确认 → 发布 `home/terminal/ack`。
- 关键实现：终端不存业务状态，只存"当前该显示什么"；断网时用本地缓存的最近 5 条提醒继续播（降级不空白）。
- 交付物：能跑的整机 + 语义表（灯色↔状态）+ 实拍视频。

**进阶阶段（约 2–3 周）**

- 摄像头 + MediaPipe Pose：人形存在、久坐提醒（"您坐了两个小时了"）。
- "跟随"：取人体框中心 x 坐标 → 舵机底座转向（别做底盘移动，室内移动机器人是另一个项目）。
- 表情：小 OLED/圆屏画眼睛（开心/等待/困），比舵机更省事、更可靠。
- 唤醒词 + 本地 ASR（Vosk 小模型）→ "我吃药了"直接落记录。

**成本**：Pi 4B ~350–450 元 + 灯环/舵机/壳/屏 ~150 元；Zero 2W 便宜但跑不动 MediaPipe。
**坑与规避**

- 供货与涨价；电源不足会导致灯环闪烁/重启（用 5V 3A 独立供电）。
- 舵机噪声大、寿命短 → 演示用"点头"即可，别做复杂动作。
- 离线中文 TTS 质量一般 → 关键提醒用预录 + TTS 混合。
- 音频回声/啸叫 → 麦克风与喇叭物理隔离，加 AEC（`speexdsp`）或直接按键触发。

**评分覆盖**：进阶 2（本体）· 进阶 1（可接自己的雷达/摄像头）· 基础靠后端
**适合**：有人愿意碰 Linux + 焊接/接线，想要"实物演示"的队伍。

#### D2 · ESP32-S3 + LVGL（最便宜的"真硬件"）

**技术栈**：ESP32-S3-WROOM-1（8 MB PSRAM）；ESP-IDF 或 Arduino；LVGL 8/9 + 1.28"/2.4" IPS 圆屏/方屏；WS2812；I2S + MAX98357A + 小喇叭；**预录 WAV**（中文语音提前用 TTS 生成好，存 SPIFFS/SD）；MQTT over TLS；可选 ESPHome（快速接 HA）。

**基础阶段（约 3 周）**

- 范围：订阅 MQTT → 屏幕大字 + 播预录音频 + 3 个物理大按钮（确认/稍后/SOS）→ 发布事件；AP 配网门户（手机连热点填 Wi-Fi）。
- 关键实现：**中文 TTS 不要放端上**。做法是把 20–30 条常用提醒文案提前合成成 WAV（电脑上跑 Piper/云 TTS），端上只按 ID 播放 → 成本为零、音质可控、离线可用。变量部分（时间、药名）用"拼接音频段"或干脆屏幕显示。
- 交付物：整机 + 3D 打印/纸板壳 + 演示视频。

**进阶阶段（约 2–3 周）**

- ESP32-S3 + OV2640 做简单存在检测（帧差/轻量模型），或接 LD2410 雷达串口（比摄像头省事）。
- 舵机做"点头/摇头"；灯带做呼吸/流水表达"在听/在等/已完成"。
- OTA 升级（`esp_https_ota`）；电池 + 深度睡眠 + PIR/雷达唤醒（低功耗）。
- 用 ESPHome 接入后，可让 HA 直接驱动（省一半代码，但自研含量下降，自行权衡）。

**成本**：整机 80–150 元，最便宜。
**坑与规避**

- ESP-IDF 环境对大一有门槛（工具链、CMake、烧录）；建议用 Arduino + 现成 LVGL 示例起步。
- 内存/性能紧张：LVGL 全屏刷新会卡，用局部刷新 + 双缓冲。
- Wi-Fi 断连要能自恢复（重连 + 看门狗复位），这是"断网处理"的硬件版答案。

**评分覆盖**：进阶 2（本体，含"动作"）· 进阶 1（串口雷达）
**适合**：预算紧、想要"自己画 PCB/接线"的硬件感，队里有人能啃 C。

#### D3 · 旧安卓手机 + 壳（低成本"套壳终端"）

**技术栈**：任意 Android 8+ 旧手机；自研 App（B2 的 kiosk 全屏模式）；蓝牙自拍杆按键改造成大按钮；3D 打印/毛绒外壳 + 支架；系统 TTS。

**基础阶段（约 1–2 周）**

- 范围：手机固定在客厅/餐桌，常亮 + 全屏 App + 语音播报 + 蓝牙按钮确认 + 摄像头人形检测（ML Kit / MediaPipe）。
- 关键实现：屏幕常亮（`FLAG_KEEP_SCREEN_ON`）+ 亮度自动 + 防烧屏（夜间降低亮度/移动像素）；蓝牙按键映射成"确认"。
- 交付物：实物 + 实拍。

**进阶阶段（约 2 周）**

- 手机当"宠物脸"：屏幕播表情动画（眼睛/呼吸），配合灯带。
- 移动：装到小车上（可选，风险高）；或"转头"用手机云台（更简单）。
- 传感器经手机热点/局域网接入（手机当网关）。

**成本**：0（旧机）+ 壳 50–100 元。
**坑与规避**

- 长期常亮会烧屏/鼓包 → 演示用即可，报告里写清"长时间使用需外接供电与散热"。
- "跟随"做不了 → 老实说这是固定终端，别硬吹。
- 观感偏"手机套壳"，需要用壳和灯把"宠物感"做出来。

**评分覆盖**：进阶 2（可，表情强/动作弱）· 进阶 1（摄像头）
**适合**：**风险最低**的终端方案，尤其适合当"兜底演示"。

#### D4 · 商用设备二次开发（HA + 智能音箱/带屏音箱）

**技术栈**：Home Assistant + 小米/天猫精灵集成（HACS 里的 `xiaomi_miot` 等）；或 ESPHome 刷 Sonoff/涂鸦设备；带屏音箱做显示。

**基础阶段（约 1 周）**

- 范围：HA 自动化 → 音箱 TTS 播报提醒；带屏音箱显示文字；老人说"好"由语音助手确认（不可靠，仅演示）。

**进阶阶段（约 1 周）**

- 多品牌设备联动（灯、插座、窗帘）；用智能插座功率判断"电饭煲在用"→ 推断"在做饭"。

**坑与规避**

- 云接口经常变（小米云 token 失效、协议升级）→ 演示前一周必须锁定版本，别升级。
- "自研"含量低，答辩会被问；只能作为**补充触达通道**，不能当主交付。
- 隐私：音箱常听，需说明数据流向。

**评分覆盖**：进阶 2（弱，"别人的宠物"）· 进阶 1（借设备）
**适合**：不作为主路线；家里正好有设备时，当"多通道提醒"的证据。

### 3.5 形态 E：定制化（不含 AOSP：老人桌面 + 专用机）

**先说清定位**：需求分析里的 Stage2 写的是"专用 IoT 设备 / 定制手机 ROM"。AOSP 已经排除（理由见 §3.3.2），所以这一节只保留三条**不编译任何系统镜像**的路：

- **E2**：把一台 **root 过的安卓机**变成"只跑我们 App 的老人机"——你们手上正好有一台；
- **E3**：树莓派 + 浏览器全屏（有 Web 前端时才用）；
- **E3-Qt**：树莓派 + Qt eglfs 全屏（**主方案用这条**，与 B4 共用同一份 QML）。

**root 让 E2 从"高风险"变成"半天"**：普通做法要恢复出厂、设 Device Owner、还不能用日常机；root 之后，换桌面就是 `set-home-activity` + 禁用系统 Launcher，隐藏状态栏是一条 `settings`，锁任务可选——不需要任何"设备所有者"仪式。

#### E2 · root 安卓 14 → 老人专用机（"80% 的 ROM 效果"，半天到 1 周）

**技术栈**：Magisk（root 本体）；自家 Launcher（可以是原生极简桌面，也可以是 Qt 应用里"带 HOME intent-filter"的 Activity）；`cmd package set-home-activity`；`pm disable-user`；`settings put global policy_control`；App 内 `startLockTask()`（可选，root 下不强制）。

**基础阶段（半天到 1 天）**

- 目标：按 Home 键回不到系统桌面；状态栏/导航栏隐藏；开机自启进我们界面；只剩 4 个大按钮。
- 命令清单（写成 `scripts/kiosk.sh`，演示前一键执行）：
  ```bash
  # 1) 装自家 Launcher 并设为默认桌面
  adb install -r ElderLauncher.apk
  adb shell cmd package set-home-activity com.you.elder/.LauncherActivity
  # 2) 禁用系统桌面（root 才做得到；想恢复就 enable）
  adb shell pm disable-user --user 0 com.android.launcher3
  # 3) 全屏沉浸（隐藏状态栏与导航栏）
  adb shell settings put global policy_control immersive.full=*
  # 4) 免打扰 + 充电时屏幕常亮
  adb shell settings put global zen_mode 1
  adb shell svc power stayon true
  ```
- **恢复脚本同样要写**：`pm enable com.android.launcher3` + `settings put global policy_control null`，并进 README——答辩时"我们考虑了怎么退出来"比"能锁死"更值分。

**进阶阶段（约 1 周）**

- 应用白名单：除了助手，只留"家人视频"（其余 `pm disable-user`）。
- 远程配置：MQTT 下发 `home/config/elder`（改字号、改作息、加计划），不用拿手机连电脑。
- 一键部署：`adb` 循环 + 设置导入，第二台机器 3 分钟配好——现场演示"批量部署"很抓眼。
- 电量与网络策略：`deviceidle whitelist`、`svc wifi` 一并进脚本。

**坑与规避**

- **禁错 Launcher 会黑屏**：先确认自家 Launcher 的 HOME intent-filter 生效、`set-home-activity` 成功，再去禁用系统的；操作前保持 `adb` 连接，黑了还能救。
- `policy_control` 在部分 ROM 上会被系统 UI 覆盖 → App 内用 `WindowInsetsController` 兜底。
- 别去改 `settings` 里不认识的键；每一项都记进 `scripts/` 并写清恢复方式。
- 系统 OTA 会掉 root、也可能重置这些设置 → 答辩前锁版本、不点更新。

**评分覆盖**：基础 4 条全（跑的就是我们自己的 App）· 进阶 2（终端可以就是这台机器）· 额外加分：专用设备感 + 可复现的部署脚本
**适合**：**你们组**——手上已有 root 机，这是投入产出比最高的 Stage2 答案，也是 E3-Qt 的"手机版"对照。

#### E3 · 树莓派 + 浏览器 kiosk（只在有 Web 前端时才用）

**技术栈**：Raspberry Pi OS Lite（或 Debian）+ `cage`（Wayland kiosk）或 X + `chromium --kiosk`；systemd 服务；看门狗；10–15 寸触摸屏；GPIO 大按钮。

**基础阶段（约 1 周）**

- 范围：开机直接进全屏 Web 应用（复用 A1/A2 的前端），无桌面、无地址栏、无鼠标指针；断电重启自动恢复。
- 关键实现：
  - `chromium-browser --kiosk --noerrdialogs --disable-infobars --incognito http://localhost:8000`
  - systemd unit：`Restart=always` + `WatchdogSec`；本地后端也由 systemd 托管。
  - 只读根文件系统（`overlayroot`）或 `fsck` 容错 → 解决"直接拔电"的可靠性（正好对应表格"重启处理"）。
- 交付物：整机 + 开机到界面的计时视频（目标 < 30 s）。

**进阶阶段（约 1–2 周）**

- 物理按键 → GPIO → 后端 API（`gpiozero` 监听）→ 真正的"一个大按钮"。
- 双屏：大屏给老人，小屏/e-ink 给家属看周报。
- 远程升级：`git pull` + 重启 脚本（或 `balena`/`ansible`，别过度）。
- 屏幕亮度按时间段自动调节；夜间变暗红色（护眼 + 不干扰睡眠）。

**成本**：Pi 4B + 10 寸屏 ~600–800 元。
**坑与规避**

- Chromium 在 Pi 上内存吃紧 → 用 `--disable-gpu` 或轻量浏览器（`wpewebkit` 麻烦，不推荐）。
- 触摸屏校准/驱动；HDMI 热插拔会黑屏 → 固定连接。
- 屏幕长期显示静态内容烧屏 → 用 OLED 慎选，IPS 更稳。

**评分覆盖**：基础 4 条全（借后端）· 进阶 2（终端就长在这台机器上）· 进阶 1（USB 接雷达/串口）
**适合**：家属端补了 A2 的 Web 页面时**顺便**复用；**本方案的主终端不走这条**（走 E3-Qt，理由见下）。

#### E3-Qt · 树莓派 + Qt eglfs（**主方案用这条**：终端兼 MQTT broker）

主形态走 Qt（B4），E3 的浏览器那一层就可以整层去掉：**同一个 Qt 应用编到 aarch64，用 eglfs 平台插件全屏运行**。而且这台 Pi 顺便承担第二份工作——**跑 mosquitto**，于是它同时是"专用设备""宠物终端""消息总线"，一件事三份分。

**基础阶段（约 3–5 天，在 B4 基础阶段完成后）**

- 用 **Pi 本机编译**（别一上来就交叉编译）：`cmake -B build && cmake --build build`，然后 `./elderly-helper -platform eglfs`；`QT_QPA_EGLFS_ALWAYS_SET_MODE=1` 保证分辨率不被改。
- systemd unit：`Restart=always` + `WatchdogSec`；无图形环境直接拉起（不需要 `graphical.target`）。
- mosquitto 一并由 systemd 托管，配置只监听内网 + 开 WebSocket 端口（给未来的 Web 家属端留路），账号用 `mosquitto_passwd` 建一个。
- 好处：**没有浏览器、没有 X、没有 Wayland 合成器**，启动路径短、断电恢复更确定；坏处：调试只能靠 SSH + `QT_LOGGING_RULES`。

**进阶阶段（约 1 周）**

- GPIO 按键直接进 Qt 的 `QSocketNotifier`（连后端都省了）；
- 宠物表情：同一份 QML 在 Pi 上是"桌面宠物的大脸"，在手机上是"会眨眼的提醒卡"——两个作业点一次拿下；
- 软键盘注意：触摸屏输入时 **Qt Virtual Keyboard 是 GPL/商业许可**（附录 C），课程可用、闭源分发不行；
- 只读根文件系统（`overlayroot`）或把数据目录放到单独分区 → 直接拔电也不坏（正好对应表格"重启处理"）；
- 远程升级：`git pull` + 编译 + 重启，或用 systemd 的 `PathChanged` 触发。

**取舍**：E3（Chromium）复用 Web 代码、调试舒服，但多一层浏览器、多一套 UI；E3-Qt 与 B4 共用 QML、启动更快、更像专用设备，代价是跨架构编译的坑（`sysroot`、Qt 库版本必须与目标机一致）。**两条只能选一条，选 E3-Qt。**

#### F1 · 毫米波雷达（存在 / 活动 / 微动）

**上手成本排序**（同一个新手从零到"稳定出帧"）：

| LD2410C | 半天 | 几乎不用卡：ESPHome 有官方 `ld2410` 组件、GitHub 一堆 Arduino 示例、海凌科有 Windows 上位机可视化调阈值 |
| LD2450 | 半天 | 协议简单（3 目标坐标），示例够用 |
| MR24HPC1 | 1–1.5 天 | 二进制帧 + 校验和要自己写解析状态机；**没有 LD2410 那种可视化调参上位机**，改阈值靠串口发命令帧；社区资料以英文为主、量少一个数量级 |
| MR60BHA1 / FDA1 | 1–2 天 | 同 Seeed 家族的通病：文档能看，示例少，参数漂移要自己标定 |

具体波特率、供电范围、标称探测距离**以各自手册为准**——这类"背数字"最容易过时，现场以第一次握手成功为准。

**技术栈**：ESP32 或树莓派串口读帧 → 解析 → MQTT 上报（`home/sensor/presence`）。

**进阶（可选，root 手机直连）**：如果 `ls /dev/ttyUSB*` 能出节点、`dmesg` 里能看到 `ch34x`，root 安卓机可以直接 `open()` 串口读 LD2410，**连 ESP32 都省了**（§2.7 R8-11）。先用 USB-OTG 线在真机上验证，出不来就老实走 ESP32 网关——别把这条当主路径，内核模块适配是个坑。

**基础阶段（约 1–2 周）**

- 范围：在/离、静止时长、距离 → "久未活动告警"（R3-3）+ "夜间起夜"（R3-4）+ 数据入库与时序图。
- 关键实现：LD2410 用工程模式（engineering mode）读每帧的距离能量，别只用"有人/无人"布尔值；去抖（连续 N 帧才改状态）避免闪烁。
- 交付物：24 h 数据曲线 + 一次真实触发的告警。

**进阶阶段（约 2 周）**

- 多雷达（卧室/卫生间/客厅）→ 活动序列 → 与个人基线比较 → 作息漂移提示（R6-1）。
- 跌倒检测：**LD2410 做不到**（它没有姿态信息）。要做必须换专用跌倒雷达或用摄像头（F3），且必须报告误报率。
- 睡眠：**MR60BHA1** 可出呼吸率/心率趋势（MR24HPC1 只是 24 GHz 存在模块，不出生命体征），但精度不能当医疗数据。

**坑与规避**

- 安装角度/高度/遮挡影响极大 → 固定支架 + 现场标定，报告里写标定过程。
- 风扇、窗帘、宠物会误触发 → 用距离门限 + 能量阈值过滤。
- 不要把"有人"直接当"在床" → 需要雷达位置 + 时间窗联合判断。

#### F1.1 · 要不要在手机端训一个模型来判断动作？（结论：不用，而且多数情况下做不到）

**1. 数据层面：LD2410C 给不出能训的东西。**
它只输出"有人/无人 + 运动目标距离与能量 + 静止目标距离与能量"，**没有原始 I/Q、没有点云、没有相位**。靠这几个标量判断"走/坐/躺/摔"训不出来——不是模型不够好，是信息量不够。想要动作信息必须换硬件：**LD2450**（x/y 轨迹，最多 3 人，90–130 元）给"在哪、怎么动"；**MR60BHA1**（60 GHz，250–350）给呼吸率/心率；**IWR6843**（900 起）才给点云和可训练的原始 ADC。350 元封顶的方案里，这几档都不进（对照见上面 F1 的返回字段表）。

**2. 平台层面：手机端只能推理，不能训练。**
Android 上的 TFLite 只跑推理；训练得在 PC 上用 TF/PyTorch 训完再转 `.tflite`。ML Kit 只有现成 API（人脸/文字/姿态），**没有雷达这一类**。"在手机上训练一个模型"这条路本身不存在——能做的只是"在手机上加载一个在电脑上训好的模型"。

**3. 工程层面：就算有数据也来不及。**
动作分类要几百段带标签的"走/坐/躺"数据，还得防止过拟合到某一间屋子、某一个人。六周课设、硬件只有 W5 三天，这是纯风险零收益。

**该做什么：规则 + 统计，而且不叫 AI 反而更好写、更好答辩。**

| 要判断的事 | 靠什么 | 要不要模型 |
| --- | --- | --- |
| 在不在屋 | presence 布尔 + 去抖（连续 N 帧） | 不用 |
| 多久没动 | ESP32 自己计时 `still_s` | 不用 |
| 夜间起夜 | 时间窗 + 距离门限（床→卫生间） | 不用 |
| 在床 / 离床 | 距离 + 时间窗联合（先做位置标定） | 不用 |
| 作息漂移 | 7 天滑窗：活动总量、首次活动时间 | 不用（个人基线统计） |
| 走 / 坐 / 躺 | 需要轨迹（LD2450）+ 速度阈值 / 区域划分 | 不用，但要换硬件 |
| 跌倒 | 专用跌倒雷达或摄像头 + 实测误报率 | 需要，且超预算 |

**想要"模型感"但不担风险**：在手机 C++ 里写一张阈值/决策表（本质是五六个 `if`），配一张状态转移图，报告里叫"基于规则的行为状态判定"。比"我们训了个 CNN，准确率 62%"体面得多，也经得起追问。

**顺带把隐私写进论证**：摄像头能做的动作识别，卧室装不了（伦理问题）；这正是"为什么用雷达不用摄像头"的加分点——**不是做不到，是刻意不做**。

#### F2 · 床垫压力传感器

**硬件**：FSR402 薄膜压力 ×4–8 + **ADS1115**（16 位 ADC）+ ESP32；或压电薄膜（测呼吸形变）。
**技术栈**：ESP32 采样（10–50 Hz）→ 滑动平均/去抖 → MQTT。

**基础阶段（约 1–2 周）**

- 范围：在床/离床/翻身次数（阈值 + 迟滞）→ 睡眠起止自动记录（R2-1 的自动版）。
- 关键实现：每个传感器单独标定（体重差异大）；用"多点压力分布变化"判翻身，别用单点。

**进阶阶段（约 2 周）**

- 呼吸率粗估：0.1–0.5 Hz 带通 + 峰值检测；**必须给误差报告**（与手动计数对比）。
- 睡眠质量评分（自定义规则：在床时长、离床次数、翻身频次）——**明确不是医学评分**。

**坑与规避**

- 薄膜传感器漂移/蠕变 → 定期归零；受潮失效 → 做好封装。
- 不能替代 PSG（多导睡眠图）→ 附录里说明 Sleep-EDF 为什么用不上（表格已提示）。

#### F3 · 摄像头视觉

**技术栈**：USB 摄像头 + **MediaPipe Pose/Hands**（Pi 4 上约 10–15 fps，降分辨率可到 20+）；或手机端 ML Kit。

**基础阶段（约 1–2 周）**

- 范围：人形存在、久坐、离开检测；**隐私设计：只存骨架关键点，不存视频帧**。
- 关键实现：关键点 → 归一化坐标 → 简单规则（髋部高度突变 + 速度 → "疑似跌倒"）；所有判定阈值可配。

**进阶阶段（约 2 周）**

- 跌倒检测（姿态角 + 下落速度 + 持续静止）；用餐动作粗识别（手到嘴的周期）。
- 家属远程查看（打码/只显示轮廓）。

**坑与规避**

- 隐私是最容易被质疑的点 → 端侧推理 + 不落盘 + 明确的开关与告知。
- 光照/遮挡/逆光误报高 → 报告里给"实验室条件下的准确率"，别吹。
- 摄像头在卧室 = 伦理问题 → 只放客厅，卧室用雷达。

#### F4 · 纯软件"活动代理指标" + 数据回放（**兜底必做**）

**技术栈**：手机传感器（计步、充电状态、屏幕解锁）+（可选）智能插座功率；**传感器回放器**（脚本按时间轴灌事件）。

**基础阶段（约 3 天）**

- 范围：用"手机解锁次数/充电时段"推断作息；写一个 `scripts/replay_sensor.py`，从 CSV 按加速时间轴往 MQTT 灌事件。
- 关键实现：回放器与真实传感器**同一 topic、同一 payload** → 上层代码完全不用改，演示时切数据源即可。

**进阶阶段（约 1–2 周）**

- 用 **CASAS Aruba** 数据集做离线分析：传感器事件 → 活动段（Sleeping/Cooking/Eating/Working…）→ 统计"做饭次数/外出时长"的周趋势 → 漂移检测。
- 产出：分析图 + 一页结论（"我们验证了方法可行，实时版受硬件限制"）。

**为什么必做**

- 硬件一定会出问题（断货、坏、现场 Wi-Fi 干扰），回放器保证**演示不翻车**。
- 它同时是"可测试性"（R7-7）的答案：没有回放器，7 天的作息规律根本没法在 1 小时内测完。

**评分覆盖**：进阶 1（"方法验证"路径，配合论文引用很加分）
**注意**：报告里必须**明确区分**真实采集与仿真数据，不能混。

### 4.1 推荐组合（默认答案）

| 业务 / 界面         | **B4**：Qt 6.8 + QML + C++（老人模式 + 家庭模式）         | 一份 QML 覆盖手机与终端；队友有经验，环境不是悬崖                                                     |
| 同步总线            | **MQTT（mosquitto）**，跑在 Pi 上                         | 手机 / 终端 / ESP32 都只连一个 broker；**不写 HTTP 后端、不做账号体系**，一台设备一个配对码就够 |
| 专用设备 + 宠物终端 | **E3-Qt**：同一台 Pi，Qt eglfs 全屏                       | 一台机器同时交"专用设备""宠物终端"两个作业点，还兼 broker                                             |
| 专用机（手机版）    | **E2**：root 安卓 14 → 禁系统桌面 + 沉浸模式             | 半天搞定，"老人机"的现场冲击力最强                                                                    |
| 感知                | **F1**（LD2410C + ESP32）+ **F4**（回放器兜底）     | 30–60 元；回放器保证演示不翻车                                                                       |
| 触达                | **G1（App 通知）+ G4（终端声光）**，G5 叙事               | 不碰短信/外呼资质                                                                                     |
| 测试与演示          | **root 安卓 14 + `scripts/chaos.sh` + 附录 D 验证清单** | 断网 / 重启 / 改时间 / 连点，全部可复现                                                               |
| 明确不做            | 小程序、AOSP、短信/外呼量产、医疗建议                           | 见 §3.3 与 §2.9                                                                                     |

**这条组合的论证（答辩一段话就够了）**：一台 Pi 同时当"专用设备""宠物终端""消息总线"，一部 root 手机同时当"老人端""家属端家庭模式""测试台"；业务逻辑只写一遍（C++），界面只写一遍（QML），硬件只通过 MQTT 进出。**硬件三件、服务一个、代码一套**——这就是"用简单结构解决复杂问题"，而且每一层都能现场演示。

**成本**：Pi 4B + 10 寸触摸屏 ~600–800 元 + LD2410C/ESP32 ~70 元 ≈ **700–900 元**（手机自有）。超预算就把屏换成旧显示器/旧电视（省 300–400），或先用 Pi Zero 2W（跑不动 MediaPipe，但跑 Qt 够）。

### 4.3 分层架构（"自由对话与提醒执行逻辑分开"的标准答案）

```
┌────────────────────────────────────────────────────┐
│  交互层  qml/       老人模式 · 家庭模式 · 语音播报   │  QML 只做绑定/动画
│  （同一份 QML 跑手机与 Pi）                          │  不含业务判断
├────────────────────────────────────────────────────┤
│  对话层  dialog/    ASR → 意图+槽位 → 受控动作       │  ← LLM 只能出"提案"
├────────────────────────────────────────────────────┤
│  领域层  core/      计划/实例状态机 · 调度 · 日志    │  ← 唯一能改状态的地方
│  (纯 C++，不 include Qt)  幂等键 · 补发策略          │  可在笔记本上跑单测
├────────────────────────────────────────────────────┤
│  适配层  devices/   MQTT(Paho) · 雷达 · 终端         │  只做协议转换
│          storage/    QtSql + SQLite                  │  只做协议转换
├────────────────────────────────────────────────────┤
│  平台层  platform/  Java 胶水：Alarm / Notify / FGS  │  ← 唯一的 Android 依赖
│  （JNI 边界，约 60 行）                              │  换平台只改这里
├────────────────────────────────────────────────────┤
│  通道层  notify/    通知 · 终端声光 · 家属转发       │
└────────────────────────────────────────────────────┘
```

两条能写进报告的判据：

- **`core/` 不 include 任何 Qt 头文件** → 全部业务规则在笔记本上编译、跑 QTest，不用模拟器、不用真机；这也是"退路 A 成立"的原因（换成 Web 时 `core/` 整段搬走，只换上下两层）。
- **`platform/` 是唯一知道"Android"存在的地方** → 编到树莓派时它整个不进构建，手机和 Pi 跑的是同一份 `core/` + 同一份 QML。

对话层的硬规则（写进报告能加分）：

1. LLM/规则解析只输出 `{intent, slots, confidence}`，**不产生副作用**。
2. 有副作用的意图（建计划、改时间、标记完成）必须经 `core/` 校验（时间是否合法、药名是否在清单里）+ **二次确认**（"你是说晚上八点吃降压药，对吗？"）。
3. 低置信度直接兜底："我没听清，我叫家人来跟您说"。
4. 所有对话动作进同一份日志，可回放。

**可用性测试的现实做法**（找不到真老人时）：

- 找 3 位 60+ 的亲属/邻居做 15 min 测试（最理想）；
- 退而求其次：让队友戴老花镜/耳塞 + 单手操作，做"限制模拟"，并在报告里**明确标注这是模拟**；
- 指标：任务完成率、平均步数、错误次数、SUS 量表（10 题，5 分钟填完）。

### 4.5 "能演示"的定义（验收脚本）

一场 5 分钟的演示必须能连续跑完这 7 件事，中间不重来（前 6 条覆盖表格基础要求 1–4，第 7 条专打"专用设备"）：

1. 家庭模式（另一台手机，或同机切换）新建"明天 8:00 降压药"→ 老人端与 Pi 终端**同时**出现。
2. 时间加速到 8:00 → 手机全屏提醒 + 语音播报 + Pi 灯变黄、表情变"等待"。
3. 点"稍后" → 5 分钟后再次提醒；连点 3 次 → 转未确认 + 家庭模式收到通知。
4. `adb reboot` → 重启后未完成提醒自动恢复（不重复、不丢）。（比拔电源更狠，也更贴近真实故障）
5. `svc wifi disable` 状态下记录一次饮水 → `svc wifi enable` → 恰好 1 条（QoS1 + 幂等键）。
6. 雷达"2 小时无活动" → 家庭模式告警 + Pi 红灯呼吸。
7. 在老人模式按 Home / 多任务键 → **回不到系统桌面，状态栏不可见**（E2 生效的证据）。

任何一条跑不过，就说明该模块还没到"能交付"。**演示前一晚必须由别人按脚本操作一遍**——自己按熟了的路径，恰恰会掩盖"老人找不到按钮"这个问题。

## 5. 需要你们拍板的 6 件事

1. **主形态就定 B4，谁主责？** 建议会 Qt 的那位做主责 + 另一位接 QML 界面，剩下两位负责 `core/` 与硬件。**W1 只做一件事：Hello World 上真机**；跑不通立刻按 §4.2 退路 A 切 Web。
2. **Pi + 屏的预算怎么定？** 新 10 寸触摸屏 300–400 元；能用旧显示器就先用旧的（演示时 HDMI 一插即可），把钱留给雷达。触摸屏的真正价值是**老人端界面在 Pi 上能直接用手点**——只有显示器时，就配个鼠标并把"降级演示"写进报告；若手边有旧平板，E3-Qt 也能跑在平板的 Linux 里。
3. **那台 root 安卓 14 不能锁成演示机。** 它同时是开发机、自动化测试台、日志来源——一旦刷成 kiosk 桌面，你调试时会连系统设置界面都进不去。**要么再找一台旧手机当演示"老人机"**，要么 `kiosk.sh` 只在演示前跑、并当场用 `restore.sh` 回滚（§3.5 E2）。
4. **传感器预算能不能到 300 元？** 能 → LD2410C（30–60）+ 备一块 LD2450 或多装一个雷达；不能 → F4 回放器 + 手机代理指标，报告里如实标注。
5. **家属端是"同一 APK 的家庭模式"还是"另写一个 Web"？** 建议先做家庭模式（配对码进同一 App，写两套 UI 是最大浪费），W6 有余力再补 Web——那时才轮到 §3.5 E3 的浏览器复用。
6. **ASR 放哪？** Pi 上的 whisper.cpp / sherpa-onnx（离线、不折腾权限、中文识别更稳）还是 JNI 调 `SpeechRecognizer`（在线、省事、要联网）？**建议 Demo 用后者、生产写前者**，报告里做一次对比表。

## 附录 B：词汇表（写报告时统一口径）

- **计划 plan**：一条规则（"每天 8:00 吃降压药"）。
- **实例 occurrence**：计划在某一天的具体一次（"10 月 29 日 8:00 的那次"），有独立状态。
- **未确认 missed/unconfirmed**：到点后超过阈值仍未确认。
- **升级 escalate**：未确认后把通知升级到下一级对象（家属/社区）。
- **幂等 idempotent**：同一操作重复提交只生效一次（靠 `event_id` 去重）。
- **kiosk**：设备被锁定为只运行一个应用，用户无法退出到桌面。
- **回放器 replayer**：按加速时间轴灌入传感器事件，用于测试与演示兜底。
- **eglfs**：Qt 的一种平台插件，不经过 X/Wayland 直接画在 framebuffer/DRM 上，全屏独占，典型用于嵌入式终端。

## 附录 C：Qt 模块许可证（选 B4 前必看）

课程项目本来就公开源码，所以下面大多"不影响"；但你们在报告里如果写"未来可产品化/可闭源分发"，这张表就是被追问的地方。**以你实际安装版本随附的 LICENSE 文件为准**，下表是常见情况。

| ---------------------------------------------------------------------------------------------------- | -------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| Qt Core / Gui / Qml / Quick / Quick Controls / Sql / Network / Multimedia / TextToSpeech / Bluetooth | LGPLv3（或商业）                             | 动态链接即可闭源分发；课程项目无影响。**别静态链接**                                                            |

| **Qt Charts / Qt Graphs**                                                                      | **GPLv3** / 商业                       | 统计图别用它，自己用 `Canvas` / `QtQuick.Shapes` 画，反而更可控                                                   |

## 附录 D：用那台 root 安卓 14 做验证（adb 清单）

root 设备最值钱的地方不是"能改系统"，而是**它让表格基础第 4 条的四类异常（重复/断网/重启/误触）从"讲故事"变成"可复现的脚本"**。下面按"要验证什么 → 怎么造 → 看什么"组织，可直接抄进 `scripts/chaos.sh`。

| 要验证的（表格原文） | 制造方法                                                                          | 观察点                                                                      |
| -------------------- | --------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| 到点真的提醒         | `appops set <pkg> SCHEDULE_EXACT_ALARM allow`，再建一条 `now+2min`            | `dumpsys alarm \| grep <pkg>` 里有 `+2m` 的 `RTC_WAKEUP`；屏幕黑着也响 |
| 待机不吞闹钟         | `dumpsys deviceidle force-idle`                                                 | 到点仍触发；未进白名单时会晚几十秒到几分钟（对比数据写报告）                |
| 重启不丢             | `adb reboot`，不动任何按钮，等 90 s                                             | 未完成实例仍在；无重复实例                                                  |
| 断网                 | `svc wifi disable` + `svc data disable`                                       | 本地能记录；恢复后云端恰好 1 条                                             |
| 弱网 / 丢包          | 在 Pi 侧加 `tc qdisc add dev wlan0 root netem delay 800ms loss 20%`             | 重连后补发不重复；界面不卡死                                                |
| 改时间 / 换时区      | `settings put global auto_time 0` + `date` / `setprop persist.sys.timezone` | 不出现重复提醒、不出现负数倒计时                                            |
| 误触                 | `input tap x y` 连点 5 次、`input swipe` 乱划                                 | 确认幂等；"稍后"3 次上限生效                                                |
| 强杀进程             | `am force-stop <pkg>`                                                           | 闹钟仍在（由系统托管）；重开 App 状态一致                                   |
| 通知到底发没发       | `dumpsys notification --noredact \| grep <pkg>`                                  | 有记录、渠道正确、免打扰下确实静音                                          |
| 前台服务活着         | `dumpsys activity services <pkg>`                                               | FGS 在跑，类型是 `specialUse`                                             |
| 崩溃定位             | `adb logcat -s Qt:V AndroidRuntime:E`                                           | Qt 层与 Java 层日志分开看，别混成一团                                       |
| 演示日兜底           | 提前做一次 TWRP 全盘备份                                                          | 出问题 3 分钟内回滚，不靠"再刷一遍"                                         |

**三条纪律**
