## 0. 一句话

QML 只调用 6 个 C++ 门面（VM）的方法、只读它们的属性；**方法只管发意图，不返回值**，
结果通过属性变化 + 信号回到界面。门面之下是后端的世界（SQLite、状态机、HTTP、MQTT），
前端不碰 `event_id`、`server_seq`、`cron`，也不在 QML 里改任何状态。

---

## 1. 分层与唯一入口

```text
qml/ 页面、组件、Fmt/Undo/Notify 三个纯 UI 单例
  │  只能 import SmartGlasses 里的 VM 单例
  ▼
src/vm/*_vm.{h,cpp}   facade（QML_SINGLETON）—— 已冻结，见 §4
  │
  ├─ src/vm/app_core.{h,cpp}   B1 的地盘：SQLite / 状态机 / 事件日志（当前是内存 demo）
  ├─ src/comm/http_client.{h,cpp}  B2 的地盘：唯一允许出现 QNetworkAccessManager 的文件
  └─ 平台层（TTS、前台服务、闹钟）  B2 的地盘
```

三条硬规则：

1. **QML 不写状态**。`state` 只有 `AppCore` 能改；页面只调 `ReminderVM.confirm()` 这类意图。
2. **QML 不拼时间戳、不生成 id**。需要"现在"用 `ReminderVM.nowMs` 或 `Fmt.now`；
   id 一律来自返回的属性（`PlanVM.createPlan` 后从 `plans` 里读）。
3. **失败不抛异常**。所有被拒绝的操作走 `commandRejected(code, message)`，
   `Main.qml` 统一弹 Toast；`code` 见 §2.4。

## 2. 全局约定

### 2.1 时间

| 用途 | 类型 | 说明 |
| --- | --- | --- |
| 事件、到期、记录时间 | `int64` 毫秒（Unix epoch） | 字段名以 `Ts`/`Ms` 结尾：`dueTs`、`snoozeUntilTs`、`at`、`nowMs` |
| 日期（统计、rule.once） | `string` `yyyy-MM-dd` | 本地时区 |
| 时刻（展示、rule.times） | `string` `HH:mm` | 本地时区，24 小时制 |
| 播报/展示的相对时间 | 由 `Fmt` 计算 | 后端不下发"3 分钟前"这类文案 |

### 2.2 ID

- `planId`、`occurrenceId`、`recordId`：正整数，`< 2^53`（QML 的 number 是 double）。
- `occurrenceId` 端上生成，公式冻结：

```text
occurrenceId = planId * 1_000_000_000
             + (julianDay % 10_000_000) * 100
             + 当天该计划第几个提醒（0 起）
```

  好处：同一条 occurrence 在端上、后端、重试之间都是同一个数，冲突时后端可直接用它做幂等键。

### 2.3 命名

- QML 侧一律 camelCase（`occurrenceId`、`dueTs`、`snoozeRemaining`）。
- rule JSON 与 HTTP 请求/响应由 B2/B1 负责转成 snake_case，**不穿透到 QML**。

### 2.4 错误码

`commandRejected(code, message)` 与 `facadeErrorText(code)`（`src/vm/facade_errors.h`）用的同一套：

| code | 触发 | 界面文案（已实现） |
| --- | --- | --- |
| `occurrence_not_found` | id 不在今日清单 | 这条提醒已经不在今天的清单里了 |
| `already_confirmed` | 对已确认的再确认 / 再推迟 | 这条提醒已经确认过了 |
| `snooze_limit` | 推迟超过 3 次 | 这条提醒已经推迟 3 次了，请直接确认 |
| `nothing_to_undo` | 没有可撤销的上一状态 | 没有可以撤销的操作 |
| `not_escalatable` | 待确认状态下直接升级 | 这条提醒还没到需要通知家人的时候 |
| `plan_not_found` | 改/删不存在的计划 | 这条提醒已经被删除了 |
| `record_not_found` | 修改/删除不存在的记录 | 这条记录已经被删除了 |
| `empty_title` | 计划名为空 | 请填写提醒名称 |
| `bad_rule_kind` | `rule.kind` 不在四种内 | 重复方式不支持 |
| `empty_times` | 非 once 规则没有 times | 请至少选择一个时间 |
| `water_goal_reached` | 已喝满 8 杯还点 | 今天的水已经喝够了 |
| `audio_unavailable` | TTS 引擎不可用 | 语音暂时用不了 |
| `bad_pair_code` | 配对码不是 6 位数字 | 配对码应该是 6 位数字 |
| `offline` | 无网络 / 同步未就绪 | 现在没有网络，稍后会自动同步 |

新增错误码必须先加进本表与 `facade_errors.h`，否则界面只会显示兜底文案。

## 3. 数据形状

所有 `QVariantMap` 的键如下，**多一个字段可以，少一个不行**（QML 直接按名字取，缺字段会静默变 undefined）。

### 3.1 occurrence（`ReminderVM.today` / `next` / `upcoming`、`reminderDue` 参数）

| 键 | 类型 | 说明 |
| --- | --- | --- |
| `occurrenceId` | int64 | 见 §2.2 |
| `planId` | int64 | 所属计划 |

| `dose` | string | 剂量，可空 |
| `note` | string | 备注，可空 |
| `dueTs` | int64 | 应做时间 |
| `state` | string | 六态之一，见 §5 |
| `snoozeCount` | int | 已推迟次数（0–3） |
| `snoozeRemaining` | int | 还能推迟几次（派生，后端也可下发） |
| `snoozeUntilTs` | int64 | 推迟到的时间，0 表示无 |
| `windowMin` | int | 有效期，默认 30；超过即 missed |
| `escalateAfterMin` | int | 提醒 N 分钟后通知家人，默认 15 |
| `repeatText` | string | "每天""每周一、周三""每月 5 日""仅 11 月 6 日"（派生，只展示） |
| `canConfirm` | bool | 界面据此禁用"已完成" |
| `canSnooze` | bool | 界面据此禁用"稍后" |

| `preview` | bool | 仅 `next`/`upcoming`：预览项，不落事件、不可确认/推迟 |

### 3.2 plan（`PlanVM.plans`、`createPlan`/`updatePlan` 的入参）

| 键 | 类型 | 说明 |
| --- | --- | --- |
| `planId` | int64 | 新建时不需要，由返回值/`plans` 给出 |
| `title` | string | 必填，去空格后非空 |

### 3.3 record（`RecordVM.records`）

| 键 | 类型 | 说明 |
| --- | --- | --- |
| `recordId` | int64 | 修订时保持不变 |
| `type` | string | `water` / `sleep_start` / `sleep_end` / `activity` |
| `value` | double | 杯数 / 分钟；睡眠起止为 1 |
| `unit` | string | `杯` / `分钟` |
| `at` | int64 | 记录时间（毫秒） |
| `correctedFrom` | int64 | 被修订的原值 id，0 表示未修订 |

### 3.4 stats（`RecordVM.stats7` / `stats30`）

端上视图模型，不是后端 `/stats` 的原始结构；B1 从 occurrence 历史本地算出即可。

| 键 | 类型 | 说明 |
| --- | --- | --- |
| `date` | string | `yyyy-MM-dd` |
| `label` | string | 7 天图例用"周一"…；30 天只在首尾与每 5 天给 `M/d`，其余空串 |
| `expected` | int | 当天应做次数（现在固定 4，按计划数算） |
| `confirmed` | int | 当天已确认 |
| `missed` | int | `max(0, expected - confirmed)` |
| `rate` | int | `0–100`，`confirmed / expected` 四舍五入 |
| `isToday` | bool | 最后一根柱子 |

> v1.1 兼容期：统计项同时保留 `done` / `total` 两个旧键（等于 `confirmed` / `expected`），
> 后端替换实现后保留其一即可，QML 已按 `expected`/`confirmed` 迁移。

### 3.5 profile（`ProfileVM`）

`elderName`、`caregiverName`、`caregiverPhone`，均为 string；配对成功后由 B2 写入。

### 3.6 事件（只在 `AppCore.eventLog()` / `SyncVM.eventLogCsv()` 出现，QML 不读）

| 键 | 类型 |
| --- | --- |
| `eventId` | string（uuid5，见 §7） |
| `occurrenceId` | int64 |
| `action` | `fire` / `confirm` / `snooze` / `undo` / `miss` / `escalate` / `pair` / `sos` |
| `ts` | int64 |
| `deviceId` | string |
| `reason` | string，可空 |
| `serverSeq` | int64，未同步为 0 |

## 5. 状态机（唯一真相在 AppCore）

```text
                 fire（到点）
   pending ─────────────────▶ notified ──confirm──▶ confirmed
      ▲  ▲                       │  │  ▲              │
      │  │                       │  │  │              │
      │  │        undo           │  │  └──undo────────┘
      │  └───────────────────────┘  │
      │            snooze            │  超 windowMin
      │        ┌───────────────────┐ │
      └────────┤     snoozed       ├─┴──▶ missed ──escalate──▶ escalated
               └───────────────────┘        ▲
                                            │ escalateAfterMin 到点（notified/snoozed）
```

| 迁移 | 触发者 | 备注 |
| --- | --- | --- |
| pending → notified | 端上 tick（`dueTs` 到） | 发 `reminderDue` |
| pending → missed | tick（已过 `dueTs + windowMin`） | 没弹过也算 |
| notified → confirmed | 用户 | 幂等；重复点击被拒 |
| notified → snoozed | 用户 | 最多 3 次 |
| notified → missed | tick | 超过有效期 |
| snoozed → notified | tick（`snoozeUntilTs` 到） | 再次弹 |
| confirmed → notified | undo | 5 秒撤销窗口由 UI 计时，但语义在这里 |
| missed / escalated → notified | undo | 允许改主意 |
| notified / snoozed / missed → escalated | 用户点"通知家人"或 `escalateAfterMin` 到点 | confirmed/pending 不可 |

**只有 AppCore 能写 state**；`VM` 做参数校验与错误码翻译，`QML` 只发意图。

## 6. rule JSON（四种，冻结）

字段名 snake_case（Node/DB 侧直接用），QML 构造时也按这个写。

| kind | 必填 | 可选 | 例子 |
| --- | --- | --- | --- |
| `daily` | `times: string[]` | — | `{"kind":"daily","times":["07:00","18:00"]}` |
| `weekly` | `times: string[]` | `weekdays: int[]`（1=周一…7=周日，缺省=每天） | `{"kind":"weekly","weekdays":[1,3,5],"times":["09:00"]}` |
| `monthly` | `day: int`（1–31） | `times: string[]` | `{"kind":"monthly","day":5,"times":["10:00"]}` |
| `once` | `at: string` `yyyy-MM-ddTHH:mm:ss` | — | `{"kind":"once","at":"2026-11-06T15:30:00"}` |

校验顺序（`AppCore::createPlan` 已实现，测试覆盖）：

1. `title` 去空格后为空 → `empty_title`
2. `kind` 不在四种内 → `bad_rule_kind`
3. 非 `once` 且 `times` 为空 → `empty_times`

`day` 超出当月天数时按当月最后一天处理（如 31 号在 2 月=28/29），不报错。

> `meal_offset` / `interval` / `course` 三种复杂规则**不在 v1.1 端上实现**；
> 需要时由照护者端配置成具体 times 再下发，避免端上重复实现自然语言规则。

## 7. 事件、去重与 event_id

### 7.1 event_id

```text
eventId = uuid5(namespace = 7b0f7d3e-3c2a-4a55-9f0e-6b1a2c8d4e11,
                name = "<occurrenceId>:<action>:<ts>:<seq>")
```

- 同一事件重试时 `ts` 不变 → id 不变 → 后端按 `event_id` 去重。
- `seq` 是同一毫秒内的递增序号，防同毫秒两条事件撞 id。

### 7.2 连点

**连点去重归状态机，不归 event_id**：`confirm` 第二次直接 `already_confirmed`，
不产生事件。测试 `repeatedConfirmLogsSingleEvent` 锁这个行为。

### 7.3 何时产生事件

`fire`（弹提醒）、`confirm`、`snooze`、`undo`、`miss`、`escalate`、`pair`、`sos`。
记录（`addRecord`）**不进事件流**，走 `records` 表单独的同步通道（见 §9）。

## 8. 与 HTTP 接口的映射

冻结的 5 个接口（`agent/接口冻结清单.md` v1.0）+ 2 个补充（v1.1 新增，需 A1 确认）。

| 端上动作 | 接口 | 频率 | 谁实现 |
| --- | --- | --- | --- |
| 配对 | `POST /v1/pair` | 一次 | B2 |
| 上传事件 | `POST /v1/events` | 每事件 | B2 + B1 队列 |
| 拉计划 | `GET /v1/plans?since=<server_seq>` | 启动 + 每 60s | B2 + B1 |
| 拉状态 | `GET /v1/state?since=<server_seq>` | 启动 + 每 15s + 推送 | B2 + B1 |
| **呼叫家人/告警** | `POST /v1/alarm` | 升级/呼救时 | B2 |
| **计划写（v1.1 新增）** | `POST /v1/plans` / `PATCH /v1/plans/{id}` / `DELETE /v1/plans/{id}` | 用户操作 | B2 |
| **记录（v1.1 新增）** | `POST /v1/records` / `PATCH /v1/records/{id}` | 用户操作 | B2 |

> v1.0 冻结清单里没有 plans 写接口，也没有 records 的落点，这是 §3 遗留的洞；
> v1.1 补了这 4 个端点。若 A1 不同意扩端点，替代方案是把计划配置整体搬到照护者端，
> 老人端只读——但那样 `PlanVM.createPlan` 就必须标成"仅照护者角色可见"。

## 9. 同步与离线

- `server_seq` 是单调游标：`GET /v1/state?since=` 返回 `next_seq`，客户端只持久化"已应用到的 seq"。
- 本地写入顺序固定：**写本地库 → 事件入队 → 尝试上传 → 收到 ack 才标 synced**。
- 无网时 `syncState="offline"`、`pendingCount` 增长，其余功能照常（提醒、记录都是本地能力）。
- 上传失败指数退避（1s/2s/4s/…上限 5 分钟），`retrySync()` 立刻重试一次。
- 冲突（409）：以服务端为准，回滚本地乐观值并 `toast("已与家人端同步")`；
  不允许客户端"赢"。
