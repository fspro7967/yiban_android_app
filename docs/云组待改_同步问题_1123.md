# 手机端 → 云组：同步相关的 4 个问题

> 2026-11-23。代码位置对应云端仓库 `timchen-beep/caremate` 的提交 `3c690b5`。
> 手机端对应改动见 PR #6（`feat/b2-records-sync`）。

我们这两天给手机端加了记录上传和计划上传，联调时发现云端有 4 处需要改一下。手机端能兜底的已经兜了，但根上要靠你们改。按急迫程度排，下面每条都写了：现象、原因（文件:行号）、影响、建议改法。

| # | 问题                                 | 急迫程度                 |
| - | ------------------------------------ | ------------------------ |
| 1 | 看板上删除计划，手机收不到           | 急                       |
| 2 | 计划改了以后，手机拉不到修改         | 急（和第 1 条一起改）    |
| 3 | 新建记录不去重，网络不好时可能记两条 | 中                       |
| 4 | `/v1` 不能删除记录                 | 低（需要先商量要不要加） |

---

## 1. 看板上删除计划，手机收不到（急）(ok)

**现象**：在看板上删掉一条计划，手机上一直还在，点"立即同步"也没用。

**原因**：看板删除走的是 `server.py` 第 2464 行：

```python
conn.execute("DELETE FROM plans WHERE id=? AND user_id=?", (parts[3], target))
```

这是把这行直接从表里删掉（硬删除）。手机拉计划用的是 `GET /v1/plans?since=游标`，你们只返回 `plans` 表里还存在、而且修改序号大于游标的行。被删的这行已经不在表里，手机永远收不到"它被删了"。

**影响**：老人手机上会继续按已删除的计划响提醒。

**实际例子**：社区医生在看板上把"每天 8:00 吃阿司匹林"删了，因为老人做完手术要停药一周。

- 如果手机端没有兜底：第二天 8:00 手机照常响"该吃阿司匹林了"。老人点"已服用"，就真的吃了不该吃的药。
- 手机端现在有兜底（见第 2 条末尾），能在下一次全量拉取时删掉它。但如果医生删完时手机正好断网（关了流量、在电梯里、信号差），这条计划会一直留到下次联网。断网时间跨过 8:00，照样会响。

医生在看板上看到的是"已删除"，老人那边其实还在提醒，两边都不会报错，所以很难发现。

**建议**：改成软删除，和 `/v1` 的 DELETE 一样，用 `save_plan(..., {"active": 0})` 把 `active` 置 0，这样 `GET /v1/plans` 会带着 `deleted: true` 返回。同时按第 2 条的办法递增这条计划的修改序号和版本号。

## 2. 计划改了以后，手机拉不到修改（急，和第 1 条一起改）

**现象**：计划在被手机拉过一次之后，不管怎么改，手机都拉不到新内容。

**原因**：

- `GET /v1/plans`（`v1_adapter.py` 第 307 行）靠 `v1_rowseq` 里每条计划的序号判断"有没有变化"。但这个序号只在 `_ensure_row_seq`（第 245–252 行）第一次读到这条计划时分配一次，之后再也不变。
- 看板修改计划（`server.py` 第 2401、2435 行调用 `save_plan`），既不递增 `v1_rowseq`，也不递增 `v1_version`。
- `/v1` 自己的写接口 `_plan_write`，只递增 `v1_version`，也不递增 `v1_rowseq`。

**影响**：只要是修改计划，不管从看板还是从 `/v1` 改，带 `since` 的增量拉取都看不到。手机会继续按旧的时间、剂量、内容提醒，也不报错。

**实际例子**：医生在看板上把"降压药 1 片，8:00"改成"2 片，7:00"。手机端分两种情况：

- **云端建的计划**：增量拉取看不到这次修改。要等手机下一次全量拉取，因为版本号相同时手机也接受覆盖，所以最多晚几分钟。影响不大。
- **手机上建、已经传到云端的计划**：老人自己在手机上建了"降压药 1 片，8:00"，上传后云端版本号是 1。医生在看板上改完，版本号还是 1。手机对自己上传过的计划只接受"比已确认版本更新"的数据（避免云端把本机设好的提醒规则改掉），看到版本号还是 1 就跳过了，**永远不会更新**。老人一直按 8:00、1 片在吃，医生以为已经改成 7:00、2 片。

另外，第 1 条的软删除也要靠这条：序号会递增以后，增量拉取才能收到删除。

**建议**：在 `save_plan`（`server.py` 第 1455 行）写库成功后，统一做两件事：

```python
v1_adapter.row_seq(conn, "plan", plan_id, bump=True)
# v1_version 里这条计划的 version +1
```

你们在 `server.py` 第 875–880 行，已经对"提醒状态变化"这样做了（"手机增量同步靠 v1_rowseq 的序号：状态一变就给这行新序号"），计划照着做就行。这样改完，看板和 `/v1` 两条路都覆盖到了，第 1 条的软删除也会自动带上新序号。

**手机端目前的兜底**：手动同步、恢复联网、以及每 5 分钟一次，用 `since=0` 拉一次全量，本机有、名单里没有的计划就当作已删除。这能解决删除，但对上面说的"手机上建、已上传的计划"，看板上的修改因为版本号没变，手机会一直跳过。所以还是需要你们改。

## 3. 新建记录不去重，网络不好时可能记两条（中）

**现象**：手机上记一杯水，云端可能出现两条一模一样的。

**原因**：手机发 `POST /v1/records` 时会带 `client_id`，每条记录一个固定不变的 UUID，重发时也是同一个。但 `v1_adapter._record_write` 新建记录时没读这个字段，`add_record`（`server.py` 第 1230 行）每次都生成新 id 写一条。如果你们已经写库了，但回执在路上丢了，手机会超时重发（最多 3 次），每发一次就多一条。

**影响**：云端的记录比实际多，统计和告警会出错。

**实际例子**：老人在信号差的地方点了"已服药"。云端已经写库，但回执丢了，手机超时重发，云端每收到一次就多写一条。

- 看板显示这顿药**吃了 2～4 次**。医生或家人会以为老人重复服药、吃多了，打电话来问，甚至判断错。
- 喝水、血压这类记录也一样：一天的饮水量翻倍，血压平均值被重复的读数拉偏。
- 如果云端有"一天服药超过 N 次就告警"之类的规则，会被误触发。

要回执丢失才会出现，概率不高，所以排"中"。但只要出现就是脏数据，事后很难分清哪条是真的。

**建议**：`records` 表加一列 `client_id`。POST 时如果这个 `client_id` 已经存在，就不再写，直接返回原来那条的 `record_id`。做法和 `/v1/events` 按 `event_id` 去重一样。

## 4. `/v1` 不能删除记录（低，需要先商量要不要加）

**现象**：对 `DELETE /v1/records/{id}` 发请求，回 422，记录没被删。

**原因**：`v1_adapter.py` 里 `path.startswith("/v1/records/")` 会把 DELETE 也交给 `_record_write`。它只认 PATCH，其余方法都走"新建"分支，请求体是空的、没有 `type`，于是 `add_record` 第 1232 行校验失败，回 422。不会新建记录，也不会删除。

**影响**：老人在手机上"撤销"一条已经上传的记录，云端那条删不掉。

**实际例子**：老人手抖把"未服药"点成了"已服药"，马上在手机上撤销。手机本地删掉了，但这条已经传到云端，云端删不掉。看板一直显示"今天已服药"，其实老人没吃。医生和家人就不会去提醒，真正漏服了也没人发现。一条"假的已服药"会把"漏服"盖住。

排"低"只是因为手机端还没把"撤销"接到云端，现在还碰不到。等撤销接上，这条就变成急的。

**建议**：在 `_record_write` 里加 DELETE 分支，调用你们现成的 `delete_record`，不是本人的记录回 404，成功回 `{"record_id", "deleted": true, "server_seq"}`。这是规范 §8 里没有的新接口，你们同意的话，手机端再接上"撤销 → DELETE"。

---

**总结**：第 1、2 条会让老人按**错误的计划**吃药，是最直接的安全问题。第 3、4 条会让医生和家人看到**错误的记录**，影响判断。

**补充**：记录的时间字段我们之前发错了，发的是 `ts`，你们读的是 `at`，导致记录时间变成了上传时间。这个已经在手机端改成 `at`，你们不用动。
